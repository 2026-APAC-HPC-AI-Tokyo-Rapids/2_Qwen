Why: the per-token dispatch counters of the combination run 39065587762
(timeline overlay, dispatch warp 0, about 4 tokens per warp, per-CTA
medians over the 4 ranks) split the ~6 us per pulled token into
expert/rank selection + source-index load 6.3-7.0 us in total, remote SF
and weight loads 5.5-6.8 us, TMA load wait 1.0 us, and local TMA store +
completion wait + arrival 9.9-11.0 us. The store-completion wait is the
largest piece and is only needed before the arrival red_add.

What changes (Decode instantiation only, under if constexpr on the SwapAB
geometry; Prefill SASS unchanged): after issuing a token's TMA store the
elected lane records the pool block and moves on. In the next iteration,
after the expert/rank selection and source-index load, it waits for the
store to have read the pull buffer (wait_group.read), issues the next
token's TMA load, then waits for full completion of the previous store
(wait_group 0) and issues its arrival red_add, before this token's remote
loads so that the release fence does not wait for them. The last pending
arrival is issued after the loop, before the combine handshake. Every
token still gets exactly one arrival after its TMA store has completed,
with the same pool block and the same metadata/SF/weight stores before
it, so arrival counts and token placement are unchanged and the output
must stay bit-identical to the image run 39053820377. The first token of
each warp (which gates the first FC1 block) is not delayed: its arrival
is issued when its store completes or when the next token's index work
ends, whichever is later, and the index work (~1.6 us) is shorter than
the store completion (~2.6 us).

The timeline overlay counts a token as pulled when its arrival is issued
and moves the deferred wait from the remote-load counter to the store
counter. The summarize script names the three dispatch counters.
