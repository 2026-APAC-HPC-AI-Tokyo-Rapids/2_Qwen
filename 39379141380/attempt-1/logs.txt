2026-10-20T06:13:28.6502607Z   QWEN_COMMIT_MESSAGE: [require-build] [cluster:aspire2ap] [build-only] Build the Firmus image with a DeepGEMM host switch for the Prefill MegaMoE 2-math-warpgroup geometry (DG_SM90_PREFILL_2WG)

Tag note: scripts/check-kernel-experiment-tags.py accepts [build-only] only
with [cluster:aspire2ap] ("[require-build] [cluster:firmus] [build-only]" is
rejected by the validate job); the ASPIRE build-only selector is the
supported CPU-only route and also materializes the Firmus archive (as in
913b88b). No GPU job runs from this commit.

Why: in the Prefill MegaMoE (control sf128 + swizzle, prefill-balanced-4096)
the FC1 K loop takes ~1400 clk per K block against 1024 clk of MMA work. With
four m64n128 SS warpgroups a K block reads 96 KiB of WGMMA operands from
shared memory (A 4 x 8, B 4 x 16) next to 48 KiB of TMA writes, 144 KiB or
1152 clk at 128 B/clk. Two warpgroups that each own a 64x256 row half with one
m64n256 accumulator read 80 KiB (A 2 x 8, B 2 x 32), 128 KiB with TMA = 1024
clk. Under the host's 640-thread Prefill launch the kernel-wide register cap
is 96 and ptxas rejects a real m64n256 WGMMA (C7602, needs >= 154), so the
header-only variant had to use RS m64n128 pairs, ldmatrix, setmaxnreg 200/24
and idle warpgroups; its bench did not shorten ML1Loop (683-703 us per CTA vs
679-716 for the control, at a 4% higher clock) and cost ML1Epi +22 us and
ML2Epi +11 us per CTA. The straightforward version needs the host to launch
the Prefill tile with 256 math threads: 64 + 64 + 256 = 384 threads, cap 168
registers, real m64n256 SS WGMMA, no idle warpgroups, no register hand-off.
This commit builds the image whose _C.so can do that; the header path is a
runtime overlay/bench patch, so the image's header and every unswitched JIT
source stay as on main.
