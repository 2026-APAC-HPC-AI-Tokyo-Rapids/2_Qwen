## Profile 経路の監査と変更

`qwen.yml` は最新 commit の profile tag から profile=true を渡し、prefill-pp4 tag で `configs/firmus-prefill-pp4.json` を選ぶ。require_build は commit 先頭の require-build tag だけで有効になる。今回は付けない。`firmus.yml` の provision は PROFILE を受け、config を共有 run directory の `source/firmus-framework.json` にコピーする。`profile_only` は provision と sbatch、完了判定、summary の全てで読まれ、PROFILE=false での誤投入を拒否する。profile-only は通常 score を要求せず、16 GPU の validation、profile client の export、run-success、Slurm COMPLETED を要求する。公式 parser は通常 pass だけに適用され、profile client は adoption score を生成しない。

provision は SHA256 を固定した Nsight Systems 2025.3.2 の deb を展開し、run directory の `nsys/` に置く。worker と validation の Enroot mount はこれを `/opt/nsys:ro` として渡す。worker の Python、validation、AIPerf は `/opt/sglang/venv/bin/` を明示しており、round 22 で直した torchrun/venv の経路を維持する。pair→prepack→Decode greedy→モデル起動の範囲は baseline と byte 一致するテストを追加した。gate の各 srun は profiler wrapper を経由せず、gate の timing も変えない。不要な enroot cleanup を復活させていない。

10/29 以降の gate 追加による mount や run directory の断線は見つからなかった。今回必要だった修正は以下。

1. PP4 かつ profile_only の別 pass では start_profile に CUDA_PROFILER だけを要求する。従来の CPU+CUDA_PROFILER と Torch CPU export は launch gap へ影響し、停止時の flush も増やす。旧 CPU profiler 経路とその fixture は他のモード用に保持し、このモードの validator では CPU trace を要求しない。
2. nsys は cuda,nvtx を取り、osrt を外す。旧 report の META_DATA_CAPTURE では OS runtime backtrace が true、閾値 80 µs だった。sample=none、cpuctxsw=none、cuda-graph-trace=node、fork-before-exec、cudaProfilerApi capture を維持し、cuda-trace-all-apis=false を明示する。新しい nsys-command.argv に profiler option も含む完全な argv を保存する。既存 nsys-worker.argv は従来どおり serving command のまま。
3. capture は profiling phase 開始から 5 秒待ち、全 worker の start ACK 後 8 秒保持する。解析・coverage 検証は ACK 後 0.5 秒から stop 要求前 0.5 秒までの内側約 7 秒に限定する。停止 ACK・flush・export tail を解析へ混ぜない。
4. 既存の node ごとの NVML query を PROFILE 時だけ loop-ms=100 にし、TZ=UTC を明示する。通常 run は loop=1 のまま。GPU reorder 後、各 worker が CUDA_VISIBLE_DEVICES の順で UUID と PCI bus を保存する。Nsight export の UUID は旧 raw で NVML UUID と一致しないため、GPU-map と Nsight TARGET_INFO_GPU の PCI address で結ぶ。数値 device ID のソートや GPU metrics typeId の bit を推測して stage を割り当てない。
5. validator は PP4 profile-only の各 Prefill GPU について内側 5–10 秒の sustained kernel、memcpy、90%以上の kernel/API process-scoped correlation、pair を示す writer grid、kernel 中の NVML clock/power 20 sample 以上を確認する。4 native report と従来の kernel-summary.json/validation.json は維持する。重い周期別集計は割当終了・回収後に行い、17 分枠を消費しない。

routing_capture_samples は未設定のまま 0。active marker は作らず、routing を CPU にコピーする overlay も追加しない。以前の routing capture 機能はそのまま残す。profile は通常 bench と別の 20/30/90 pass であり、今回は通常 pass 自体を省く。

## Capture と overhead

- Prefill は3 worker×PP4の12 GPU、Decode も4 GPU。nsys の process tree と全 CUDA stream の kernel、memcpy、memset、launch/synchronization API を記録する。stream filter は設けない。PP の copy engine と NCCL kernel を別に認識できる raw を保存する。
- Nsight GPU counters は従来どおり driver が unrestricted counters を公開する場合に限り cuda-visible/1000 Hz。スキップ理由も保存する。clock/power の必須経路は権限に依存しない NVML の SM clock/power/throttle CSV。
- NVML の設定周期は100 ms、目標10 Hz。実際の間隔は query 時間で延びるため、validation.json に sample 間隔の分布も残す。nsys GPC Clock の旧 export は MHz ラベルでも約1.4e9などの raw値を持つため、これを未確認の単位変換や typeId→GPU 推測で SM MHz にしない。
- backtrace、OS runtime trace、全 CUDA API trace、CPU sampling/context switch、Torch CPU activity/shape/stack を今回の PP4 profile-only では取らない。Decode の既存 CUDA graph について node trace は維持する。
- Nsight/CUPTI と NVML 自体の overhead は残る。新 run の profile window と同 run の profiler 開始前の serving batch log を比較して周期の歪みを見る。profile client の値を通常 score として採用せず、過去3回の通常 score を置き換えない。

## 解析 script と手順

`scripts/analyze_prefill_profile.py` は read-only SQLite を読み、JSON と同名 Markdown を出す。各 stage の target MegaMoE を24/24/24/22個ごとに区切った**回転周期**で、隣接 anchor の間を分析する。request ID や真の層0境界を推定したとは扱わない。各周期に target QKV/O が2L回あることを要求し、window の両端の不完全な周期を捨てる。writer grid と serving log で pair を確認する。P3等の gate selection が基準と異なれば、それをPと称して報告せず来歴に記載する。gate の条件を変えてPを強制はしない。

区分は MegaMoE、FA3、QKV/O GEMM、writer/pack、norm、router/gate、MoE input、PP send/recv or copy、lm_head/draft、other。PP3 tail は既知の LM-head GEMM 名から次の target QKV までを認識し、NCCL は tail 中でも通信区分に残す。未知の名前は other として full kernel-name 辞書に保存し、勝手に既知区分へ埋めない。residual等も名前を追える。

周期ごとに category の summed kernel duration、category union、複数区分が重なった overlap、compute kernel union、NCCL-only、copy-only、全 stream の真の idle を出す。加算できる恒等式は `period = kernel_union + copy_only + gpu_idle`。summed category time や個別の中央値を単純加算して周期へ合わせない。

全 gap に直前・直後 kernel の StringId と辞書、次の launch API の start/end/process/correlation、同期待ちの候補、分類、pre-API idle を保存する。集計の pre_api_idle_lower_bound_us は根拠が得られた候補の下限であり、未分類 gap の費用をゼロと主張しない。correlationId は process GlobalId と組み合わせ、他 rank の同じ番号へ誤結合しない。late launch、synchronization wait、transfer wait は候補として示す。既に enqueue 済みで動かない区間と原因不明は独立に残す。CUDA API だけで host の Python 待ち、remote flag、全 stream event 依存を完全に証明できるとはしない。

clock/power は同じ report の capture UTC epoch と worker の UUID/PCI map で同 run の NVML を接続し、kernel が動いていた sample の中央値を周期ごとに出す。短い周期に sample が無い場合は null。FA3 は prepare を含む bundle、writer/pack は合計をLで割り、単独 gate の値との比を出す。gate の clock を serving に移植した予測速度や c の確定値ではない。

回収後、展開した raw を読み取り専用の入力として、出力は作業用 directory に指定する。例の ROOT はその run の回収先で、profile/ と logs/ が直接見えるようにする。実際の archive が二重 directory ならそれぞれの内側を使う。各コマンドは1物理行。

```sh
nsys export --type=sqlite --output=WORK/nsys-prefill-0.sqlite ROOT/profile/nsys-prefill-0.nsys-rep
uv run --no-project --python 3.12 python scripts/analyze_prefill_profile.py WORK/nsys-prefill-0.sqlite --output WORK/prefill-0.json --capture-log ROOT/logs/profile-capture.log --gpu-map ROOT/profile/gpu-map-prefill-0.csv --telemetry ROOT/logs/gpu-telemetry-g1.csv ROOT/logs/gpu-telemetry-g4.csv
```

prefill-1/2 も同じ要領で実施する。GPU hostname は run の実ファイル名を使う。JSON の kernels/copy/idle と gate ratios を確認し、other の大きい kernel と launch 候補を raw で確認する。新 run 後には失敗も含め tracker を手で更新する。request latency や公式 score の結論をこの profile 単独から出さない。

- **CUDA graph の候補は閉じる。** 周期の 98〜99% は kernel が埋めている。launch の遅れが下限として見えるのは worker 2 の PP0（約 8 秒で合計 76 ms、1 周期あたり平均約 1.3 ms）が最大だが、PP0 は kernel の和集合が律速の stage より短く、周期を直接決めていない。graph の判断基準（露出した launch の空白が 150〜250 µs/周期以上で周期を決めていること）は満たさない。
- **単独 gate との差の主因は電力上限の clock。** serving では 685〜691 W、SM 1410〜1455 MHz に張り付いている。同じ run の prepack gate で 650 W 以上の区間の clock は 1590〜1650 MHz（worker 0）で、serving より 12〜15% 高い。単独 gate の kernel 時間にこの比を掛けて補正することはしない（gate は複数 shape と variant の合成）。数えていなかった kernel は、MoE 入力 2.9 ms、norm 1.5 ms、その他 0.2 ms で、周期の約 4%。
- **律速の stage。** worker 0、1 は PP0〜PP2（和集合 110.3〜112.5 ms）。worker 2 は PP2 で、clock 1410 MHz、和集合 113.61 ms が他の worker の PP2 より 2.3〜2.8 ms 長く、周期 115.6〜116.2 ms を決めている。PP3 は 1〜5.4 ms の空きがある。ただし 1 層は約 4.7 ms なので、層の配分を 1 層動かすと PP3 が律速になり改善しない。
- **消費エネルギー。** 時間で按分すると、1 周期 78 J のうち MegaMoE 約 44 J、dense 約 16 J、FA3 約 13 J。kernel ごとの実測ではない。clock を上げるには、これらの kernel の命令や byte を減らす必要がある。

**round 22 の訂正：Decode greedy 融合は serving で動いていなかった。**
- **原因：** patch（`patches/sglang/decode-greedy-verify.patch`）の有効条件、graph の logits buffer、`kernels/fa3-verify/wrapper.cpp` の TORCH_CHECK、gate（`scripts/select-firmus-decode-greedy.py`）が、語彙幅を 152064 と決め打ちしていた。実モデル（`/scratch/models/Qwen3-235B-A22B-Instruct-2507-FP8/config.json`）の vocab_size は 151936。
- **trace での確認：** cast の grid（52228×512÷176＝151936）、残っている FP32 cast・dense penalty・通常の argmax、融合 kernel の不在。
- **評価の訂正：** gate の合格（0.12〜0.16 ms 短縮、bit 一致）は 152064 列の合成入力での結果。round 22 と 23 の 10025.16、10024.51 は、融合のない Decode の score である。
- **修正の方針：** 語彙幅を実モデルの値から取る。この修正は build を伴うので、次の投入にまとめる。Prefill が律速なので、score への効果は小さい見込み。

### 次の候補（gpt-6-astra、根拠の強い順）

1. **Decode greedy 融合を実際の語彙幅 151936 に合わせる。** 実装の不整合の修正で、Prefill の clock は上げない。
2. **Prefill の norm_quant で、二乗和を FMA で累積する。** 15 命令/thread を減らす。感度は周期の約 0.13%。
3. **norm_quant の residual 出力で、shared memory による並べ替えをなくす。** 約 131 MB/層の SMEM の往復を減らす。正の時間の見積もりはまだない。

2 と 3 は同じ kernel が対象で、利得は加算しない。10.2k に届く根拠ではない。
