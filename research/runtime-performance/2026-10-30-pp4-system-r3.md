# 2026-10-30 PP4 round 3：kernel より上の手（系の模型の再校正、Decode 出力の周期停止、concurrency）

読み取りのみの解析と CPU 検証（GPU job・Actions・ssh なし）。対象は run 40925558339
（9590.42、c225、Decode 上限 48）。比較に 40883389891（9392.85、上限 44）、40825417205、
EP4 の 40630160781・40480817670 の archive を使った。模型は
[`pp4-serving-model.py`](pp4-serving-model.py)（v2）、結果は
[`pp4-serving-model-20261030-r3.json`](pp4-serving-model-20261030-r3.json)。

## 1. 要約

- **Decode の出力が 14〜19 s ごとに約 0.33 s 止まる。** 調べた 5 run（PP4 3 本、EP4 2 本）
  すべてで、profiling 中に 6〜7 回起きる。Decode scheduler は止まらずに step を続け、
  router が保持していた最初の token も出続ける。止まるのは Decode server の出力経路である。
  閉ループの client は完了を受け取れないので新しい要求を出さず、Prefill の待ち行列が
  空になる。
- **9590 の run では、この停止が Prefill の容量を約 1.0% 削っている。** 停止の前後
  （−1〜+3 s）を除いた周期は中央値の +0.15% しかない。40883389891 では同じ停止の損失が
  0.07% だった。差は Prefill の待ち行列の深さで、1 pipeline あたり平均 5.5 から 3.9 に
  減っている。Decode の上限を 48 に上げた結果、Decode に入る要求が増え、225 件のうち
  Prefill に並ぶ分が減った。
- **実装したのは 2 つ。** (1) 準備の要求を流した後、AIPerf を始める前に、全 server の
  `/freeze_gc` を呼ぶ。SGLang の tokenizer、scheduler、detokenizer で、起動時の heap を
  Python の GC の対象から外す。(2) concurrency を 225 から 232 に上げる。
  模型では、両方入れて **+0.68%（9590 → 約 9,655）**。GC の凍結が効かなくても、
  c232 だけで +0.40% になる。
- **Prefill −3%・Decode −5% と組み合わせた場合の予測は約 10,020（c225）** である。
  Decode が速くなると Decode 中の要求が減り、最適な c は 225 に戻る。c232 のままだと
  約 10,000。
- **10,000 と 10,300 の条件**（GC 凍結あり、c と上限は各点で最良）は次のとおり。
  - 10,000：Prefill −4% と Decode −2%（10,006）。安全側は Prefill −4%・Decode −4%（10,072）。
  - 10,300：Prefill −6%・Decode −6%（10,301）、Prefill −8%・Decode −4%（10,347）、
    Prefill −6%・Decode −8%（10,335）のいずれか。
- **変えなかったもの。** tail node での GPU の割り当て、microbatch の大きさ、async depth、
  段の分割、Decode の上限は変えなかった（§5）。開始時の不合格（122 件）は、ほぼ容量で
  決まっている。残る改善は、Prefill の 3 番目の microbatch で全 pipeline に毎回起きる
  約 0.1 s の停止だけである（模型で +0.33%、原因は未特定）。

## 2. 模型の再校正

v1 から 4 点を変え、40925558339 に合わせた。

- Decode の出力停止（周期 15.2 s、長さ 0.33 s、位相は seed ごとに乱数）を入れた。
- 開始直後の 3 番目の microbatch の遅れ（0.10 / 0.10 / 0.22 s、Prefill log から）を入れた。
- 1 要求だけの microbatch は周期の 0.53 倍で終わる（実測 62 ms / 117 ms）。v1 は周期を
  まるごと使っていた。
- 一斉投入の要求は保持と Decode 受け入れの遅れが短い（start_cut 0.20 s）。定常の
  admission は 60 ms、Prefill の通知は +60 ms。
- Decode の step は 38.0 ms（n=43.2/rank）、傾き 0.55 ms/要求。n で分けた中央値
  （n=40 で 36.2 ms、46 で 39.7 ms）から求めた。log の OLS は 0.36 で、0.35〜0.75 の
  感度を §4 に示す。

## 3. Decode 出力の周期停止

出力停止の検出方法：client の chunk 到着の合計が、150 ms の窓で定常の 10% 未満に
なった区間を停止とした。

| run | 構成 | 停止（profiling 開始からの s、長さ） | 間隔（s） |
|---|---|---|---|
| 40925558339 | PP4、上限 48 | 21.5, 36.5, 52.4, 67.0, 82.6, 96.7, 112.1（0.29〜0.36） | 14.0〜16.0 |
| 40883389891 | PP4、上限 44 | 23.6, 38.4, 54.7, 70.2, 85.7, 101.7（0.30〜0.39） | 14.9〜16.3 |
| 40825417205 | PP4 | 15.3 から 7 回（0.33〜0.37） | 14.2〜16.5 |
| 40630160781 | EP4 | 24.2 から 6 回（0.31〜0.38） | 16.7〜18.9 |
| 40480817670 | EP4 | 21.5 から 6 回（0.32〜0.41） | 15.8〜18.8 |

- **停止の場所。** 停止中も Decode の log の gen throughput は落ちない（scheduler は動いて
  いる）。router が保持していた最初の token は、停止中も 50 ms あたり 2〜4 件出る
  （router と client は動いている）。止まるのは Decode server の出力経路で、tokenizer
  manager か detokenizer にあたる。
- **原因の見立て。** 長さはどの構成でも 0.33 s でほぼ一定である。負荷が高い PP4 では
  間隔が短い。これは、起動時にできた大きな heap を Python の世代 2 の GC が走査する
  ときの振る舞いと合う。SGLang 自身も、長い GC を検出したときの警告で、準備の要求を
  流した後に `freeze_gc` を呼ぶよう勧めている。
- **損失。** 停止で完了が 0.33 s 遅れると、client は約 17 件の新しい要求を出さない。
  Prefill は待ち行列を使い切って止まる（02:17:13 の例：1 要求の microbatch 1 回、
  周期 166/128/126 ms、inflight は 10 から 7）。

| run | Prefill 待ち行列の平均（/pipeline） | 停止の前後を含む周期 | 前後を除く周期 | 停止による損失 |
|---|---:|---:|---:|---:|
| 40883389891 | 5.5 | 120.84 ms | 120.76 ms | 0.07% |
| 40925558339 | 3.9 | 118.31 ms | 117.14 ms | **1.0%** |

模型では、停止を除くと c225 で +0.35% になる（実測の 1.0% より小さく出る）。

## 5. 手ごとの評価

| 手 | 模型（停止なし、c225 の 9596 に対して） | 判断 |
|---|---:|---|
| GC 凍結（停止を除く） | 現状 9563 → 9596（+0.35%）。実測の損失から +0.8% まで | **実装** |
| c225 → 232 | +0.33%（停止ありでは 9563 → 9601、+0.40%） | **実装** |
| c240 | 停止あり +0.40%、なしでは +0.15% | 232 より不利 |
| 開始時の 3 番目の microbatch の遅れを除く | 9629（+0.34%、一斉投入の合格 +8） | 原因未特定。§6 の 1 |
| 一斉投入だけ最初の token の保持を外す | 9616（+0.20%、合格 +12） | 負荷に応じて SLA を見る形になり、規約上グレー。行わない |
| 全要求で保持を外す | ITL が +1.4 ms で p99 が 20 ms に近づく（EP4 の実測 −0.29%） | 行わない |
| Decode を g1 へ、Prefill の 2 本を g4 へ | −0.31%（Prefill −6%・Decode −5% でも、最良の c どうしで −0.36%） | 行わない |
| 3 要求の microbatch（1 token あたり −1.9 / −3.0 / −4.5%） | c240 で 9554 / 9591 / 9648 | 4.5% でも +0.2% 程度。行わない |
| async depth 2 | −1.9%（c225）、c240 で ITL 不合格 15 | 行わない |
| Decode の上限 44 / 52 | c225 で −0.08% / ±0 | 48 のまま |

- **tail node 内の Prefill/Decode の GPU 割り当て。**
  - g4 の 8 GPU は待機電力が 112〜116 W ある（g1 は 80〜83 W）。待機温度も 2〜4 °C 高い。
    700 W の上限で計算に使える電力が約 5% 少なく、PP4 の Prefill の clock は g1 より
    2.4% 低い（1397〜1411 MHz に対して 1419〜1459 MHz）。
  - 同じ MegaMoE の選定 kernel（SW power cap の状態で計測）は、g1 の平均に対して
    g4:0〜3 が +2.65%（40883389891）、g4:4〜7 が +1.84%（40925558339、prefill-2 の選定が
    たまたま 4〜7 で走った）遅い。遅さは node 全体の性質で、どちらの半分にもある。
  - 半分どうしの差は 0.8% で、GPU ごとの雑音（±1〜2%）と同程度である。順位も serving と
    逆転する（g4:3 は選定 kernel で最速、serving で最遅）。
  - g4:4〜7 の Decode での clock（1839 / 1870 / 1823 / 1902 MHz）は、Prefill の速さとの
    換算ができない。
  - 入れ替えの期待値は prefill-2 の ±0.5%（容量で ±0.15%）で、Decode 側にも同じ大きさの
    未知の変化が出る。行わない。
  - 遅い node を Decode から Prefill 側へ移す案は、上の表のとおり負ける。
  - NVLink は NVSwitch の全対全、PP 段間の copy engine は node 内、KV は prefill-2 から
    Decode へ node 内で送る。どの割り当てでも同じで、topology は判断を変えない。
- **開始時の不合格。**
  - 一斉投入の 225 件は同時に送られるので、送る順も 3 pipeline への振り分けも合格数を
    変えない。どの pipeline も 3 s を超えて飽和している。
  - Decode の GPU が開始直後に空いていても、Prefill を Decode で行うのは Basic では
    不可（公式規約 Q1）。
  - 3 番目の microbatch の遅れは、40883389891 と 40925558339 の両方、warmup と profiling の
    両方の開始で、全 pipeline に出る（+0.09〜0.10 s、prefill-2 は +0.22〜0.33 s）。その
    時点で 5〜9 件が待ち、28〜53 件が bootstrap 中だった。
- **microbatch と async depth。** 周期 117 ms でも、CPU の起動（25 ms/microbatch）は
  depth 1 の余裕の中に収まる。depth 2 は遅延を増やすだけで負ける。3 要求の microbatch は、
  遅延が 1.5 倍になり一斉投入の合格が 104 から 87 に減るので負ける。
- **段の分割と GPU の順。** 40925558339 の telemetry で、各 pipeline の最終段の GPU は、
  24 層の段で最も遅い GPU より速く回っている。
  - g1:6 は 1446 MHz（最も遅い段は 1433）。
  - g1:3 は 1423 MHz（同 1419）。
  - g4:2 は 1411 MHz（同 1397）。

  最終段は EP4 で最も遅い GPU なので、仕事が 1〜2% 軽い分を吸収している。1 層は 4.2% に
  あたるので分割は動かせない。g1 の 8 GPU を 2 本に分け直しても（EP4 の clock で 3002 対
  現行 3008）得はない。現状のままとする。

## 6. 実装

- `platforms/firmus/framework-comparison/sglang.sbatch`
  - 準備の要求（sanity chat）の後、AIPerf の前に、`worker-endpoints.tsv` の全 server へ
    `POST /freeze_gc` を送る。応答は `logs/freeze-gc.log` に残る。失敗しても job は
    続き、GC は元のままになる。各 process の log には `Freezing GC in ... gen2: X->Y`
    が出て、heap の大きさが分かる。
- `configs/firmus-prefill-pp4.json`：concurrency を 232 にする。Prefill の
  `--max-running-requests` も同じ値になる。
- 試験：`qwen-experiment-metrics/tests/test_firmus_freeze_gc.py`。呼ぶ位置（準備の要求の
  後、AIPerf の前）、全 endpoint に送ること、1 つが失敗しても続くことを確かめる。
- job 内の追加時間：HTTP 4 回と各 process の `gc.freeze`、合計 5 s 未満。image の
  再 build は不要。
- **判定**（次の serving）
  - client の export で停止が消えたこと。§3 の方法で 150 ms 窓の chunk を数える。
  - 停止の前後の Prefill の周期が中央値に近いこと。
  - Prefill の待ち行列の平均が 1 pipeline あたり 5 前後になること。
  - 停止が残る場合は、次の run で Decode に `--gc-warning-threshold-secs 0.1` を付けて
    tokenizer manager の GC かどうかを見る。今回は付けない。Decode の起動行が提出
    package と食い違い、`test_submission_package.py` が落ちるため。
- **予測**（較正の差 +0.29% を補正した値）
  - この 2 つだけ：約 9,655（GC 凍結が効かなければ約 9,630）。
  - Prefill −3%・Decode −5% と組み合わせた場合：c225 で約 10,020、c232 で約 10,000。
    この組み合わせが入るなら c は 225 に戻す（§4 の c_opt）。

## 7. 実装しなかった手（順位順）

1. **開始時の 3 番目の microbatch の遅れ**（+0.3%）。最初の 2 s の時間線を取って原因を
   特定する。profiling の開始から nsys で捉えるか、`_qpp_step` の各段に時刻の log を入れる。
   bootstrap の殺到か、最初の結果の経路が疑わしい。
2. **c を、入った kernel の組み合わせに合わせる**（外すと 0.2〜0.35%）。
   c_opt ≈ 232 + 375 ×（Decode 倍率 − Prefill 倍率）。
3. **一斉投入の最初の token の保持**（+0.2%）。負荷に応じて保持をやめる案は規約上グレーで、
   主催者への確認が要る。
4. **g4 の待機電力**（g1 より +32 W/GPU）。node の設定（clock・電力の状態）の違いなら、
   管理者に問い合わせる価値がある。prefill-2 の周期 2.6% の遅れの原因である。
