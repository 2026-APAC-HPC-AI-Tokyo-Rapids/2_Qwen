# カーネル最適化マップおよび実装ロードマップ（2026-10-03）

> 本書は実装前の調査記録。実装・実測の現状と、後続の「変更をまとめて評価する」ユーザー方針は[実測台帳](2026-10-03-kernel-campaign.md)を参照。

採用された Qwen3-235B-A22B/H100 ワークロードにおいて、最も強力な設計方針は**不要な行と中間メモリトラフィックを排除し、その上でプレフィルおよびデコードの形状に合わせて実行を特化させること**である。すべての演算を単一のライブラリに置き換えることや、FP32 中間値を削除することは、根拠によって支持されていない。既存データから実証されているのは実装上の具体的な無駄であり、大域的に最速のカーネルや、以下に提案する内容による実測されたゲインではない。

本書は、固定されたソースコードの監査、既存の Nsight トレース、4 件の追加 CPU 比較、および過去のシミュレータ感度分析を統合したものである。新規の GPU 実行、カーネルのデプロイ、またはソースミラーの修正は実施していない。実質的なレビューは GPT-6.1-Sol に委任され、日本語ドキュメントの維持管理は agy で行われた。

## スコープと数値規約

参照対象: SGLang `fc275674a97d78553b22597ee72c8fd48f5420f4`、16 H100、TP4/EP1、8P/8D、EAGLE3 steps3/draft4、BF16 dense draft、ターゲットは FP8 重み/活性化および FP8 KV。プレフィル MoE はネイティブ CUTLASS、デコード MoE は Triton、対象となる dense FP8 射影は DeepGEMM を使用、アテンションは FA3。ターゲットは 94 レイヤー、128 エキスパート、top8、H4096、TP あたりのエキスパート中間層次元 384 を持つ。ドラフトは独立した 1 レイヤーの dense モデルであり、MoE ではない。

重み、top8、ターゲットの検証、マスク/位置情報/キャッシュマッピング、および標準 SGLang レベルの数値品質を維持すること。丸め順序の変動や貪欲生成テキストの相違のみを理由に候補を棄却してはならない。既存の FP8 境界は引き続き許容されるが、FP8 以下のキャストを新規導入してはならない。同等品質の代替案が根拠によって示されない限り、FP32 リダクション/正規化/ソフトマックスおよびネイティブ RoPE 演算を維持すること。最終出力が FP8 であることは、先行する FP32 演算が冗長であることを意味しない。レジスタ変換、メモリーコピー、view、および算術リダクションはそれぞれ異なるコストである。

## 全経路最適化マップ

優先度 A は、限定的かつ具体的な初期実装を意味する。B は、より強力な要因特定を要する大規模なカーネルプロジェクトを意味する。C は、未証明の最適化仮説を意味し、本格的な実装の前に根拠を取得する必要がある。優先度はエンジニアリング上の期待価値であり、実測された速度ランキングではない。

NIXL におけるすでに int32 である配列の冗長なコピーは、独立した CPU 最適化である。これは GPU カーネルの高速化ではない。一般的な KV コーデックや新たな低精度コレクティブ通信フォーマットは優先されない。実際の圧縮率、転送の露出度、および精度の互換性が実証されていないためである。

## 最高価値の変更を実装する方法

### 1. GEMM コアを書き直す前に中間値を排除する

まず `sglang_per_token_group_quant_fp8(x,128,fuse_silu_and_mul=True)` から着手する: BF16[R,768] → 既存の FP8[R,384]、scales[R,3]。T8192、R65536 において、単独の BF16 活性化を排除することで、ランク・レイヤーあたり 96MiB の論理読み書きを回避できる。Hopper のスケールフォーマットとエキスパート順序を維持すること。MXFP8、非互換な TMA/ソート済みレイアウト、フック、LoRA、および代替の活性化形式は除外する。現行の融合 SiLU 式および丸めは異なる。ユーザーポリシーはこの差異を許容しているが、モデル品質の向上を主張するものではない。

将来的な gate-up GEMM エピローグには SiLU と量子化も組み込むことが可能であるが、これは無償の拡張ではない。対応する gate/up チャネル、および各量子化グループの 128 個の全値が同時に揃っている必要がある。既存の N タイルはこれらの依存関係を CTA を跨いで分割してしまう可能性がある。正しい設計では、得られるゲインを打ち消すようなグローバル中間値や同期を追加することなく、ペアとなる gate/up タイルとスケールリダクションのオーナーシップを配置しなければならない。これは、すでに利用可能な活性化融合とは切り離して評価すること。

down/combine において、単に BF16 のアトミック加算を用いると、アキュムレーション精度が低下し、競合やゼロクリアが発生する。より忠実な設計では、ルーティングされた 8 つのエキスパートからの寄与に対して、1 つの出力タイルに FP32 アキュムレータを割り当てる。これにより、スケジューリングの反復、エキスパート重みの再利用性の低下、またはレジスタ/共有メモリーの消費増加が生じる可能性がある。FP32 グローバルスクラッチ領域と後段のリダクションの組み合わせでは、トラフィックをほとんど削減できない可能性がある。これは比較対象の選択肢であり、確定した解決策と見なしてはならない。単一の巨大な汎用 MoE カーネルを無理に構築するのではなく、プレフィルのスループット向け設計とデコードのレイテンシ向け設計を個別に維持すること。

### 2. 単に隠蔽するのではなく回避可能な作業を排除する

通常の EAGLE draft-extend では、ヘッド射影の前に受理された行の選択がすでに判明している。既存の `draft_extend_select_index` サポートを接続し、グラフインデックスバッファと後続の選択処理を更新し、すべての条件付け隠れ状態を保持する。ターゲットの検証行や、2 回の再帰的ドラフト forward を刈り込んではならない。logprobs や確率コンシューマが必要とする場合は、完全なロジットを保持すること。

グラフパディングに関して、バケット 13/15 は小さなランタイム実験である。より根本的な有効行パスでは、形状およびキャプチャの互換性を維持しつつ、ダミー行がルーティング、グルーピング、GEMM に混入するのを防ぐ必要がある。アテンションおよびコレクティブ通信は引き続き有効な静的バッファを必要とする。実際のエキスパートヒストグラムによって、グラフのダミー行と実際のエキスパートタイル内のパディングとが区別される。これらの要素を独立した割合のゲインとして合算してはならない。

エキスパートパッキングにおいて、ヒストグラム/スキャッターは 2ER 回のスキャンに対するアルゴリズム上の代替案であり、速度向上を保証するものではない。ルートからトークンへのマッピングおよび重みを維持すること。GEMM 内部での入力ギャザーは複製を省けるが、合一アクセスや重み/入力の再利用性を損なう可能性がある。パッキングカーネルの時間だけでなく、E2E の MoE 全体で比較すること。デコード Triton はすでにプレフィルのような複製を行わずにインデックス付き入力を読み取っているため、同様の変更をデコードに適用しても、存在しない処理を対象にすることになる。

### 3. 演算精度を落とさずにアテンションの前処理を融合する

まずネイティブ RoPE を維持し、既存の K/V 変換 + キャッシュスキャッターを融合する。その次にネイティブ CUDA RoPE/格納への拡張を検討する。FP32 での回転およびオプションのスケール除算を維持し、必要に応じてレジスタ内で BF16 丸めを使用する。必要な演算ではなく、中間的なグローバルストア/ロードを排除すること。初期段階では Q 変換を分離したままにしておく。その後の FP8-Q 出力規約は FA3 のスケール、データ型、およびオーナーシップと一致していなければならない。

QKnorm/RoPE の融合には、FP32 での正規化リダクションおよび正確なイプシロン/ガンマが必要である。既存のフラグでは全レイヤーで位置情報が int32 にキャストされているため、int64 をサポートするか、変換を 1 回だけに巻き上げる。名前の付いた融合カーネル単体だけでなく、結果として生じる完全なグラフ全体をカウントすること。デバイスノード数の削減が同数の Python 呼び出し削減につながると推測してはならない。過去の実行履歴においてすでに CUDA Graphs が使用されているためである。

### 4. コンシューマ側で通信を削減する

貪欲法専用の語彙交換は、具体的な情報量の削減である。全語彙を送信する代わりに、局所最大値とグローバルトークン ID を送信する。正確な同順位順序、有効/パディングされた語彙、NaN/Inf ポリシー、およびプロセッサへの配慮が必要となる。dense ヘッドの行列積は引き続き必要である。argmax を融合すると、その行列積の出力テンソルを書き出さずに済む可能性があるが、これは別のカーネル開発として評価する。初期ドラフトプレフィルや top-k > 1 のパスは確率を消費するため、単純な argmax への置き換えの対象外である。

レイヤーの all-reduce は非線形演算に入力されるため、任意のレイヤー間で無秩序に連結することはできない。既存の融合ですでに 187 の境界がカバーされている。隣接する norm → quant の拡張は、その group128 スケールレイアウトと BF16 コンシューマを遵守できる場合にのみ適用すること。量子化された活性化を再利用するのではなく、残差およびルーターの値を保持すること。より大規模な persistent カーネルはデータをローカルに保持できるが、占有率を低下させ、コレクティブ通信の進行を妨げる可能性もある。現在のプロファイルにおいて、それが優れていることを証明するものはない。プレフィルの融合しきい値は、やみくもに引き上げるのではなく、現在の大きなメッセージのタイミングとリソース測定に基づいてのみ再検討されるべきである。

## プレフィルとデコードには異なる特化が必要である

プレフィルでは、高い持続的な GEMM スループットと、大規模な中間トラフィックの最小化が求められる。活性化の融合、ルーティング/パッキング、および down/combine の設計を優先すること。パッキングを排除するとその恩恵が失われる可能性があるため、連続したエキスパート GEMM を強力な比較ベースラインとして維持すること。

デコードは、はるかに小さなエキスパート M で動作する。ダミー行の排除、低コストな融合、アクティブタイルのスケジューリング、および同期の露出抑制を優先すること。現在の Triton 設定は、小さな形状に対してすでに M16 を使用している。論理 M をさらに小さくしても、ハードウェアの MMA 処理が必ずしも減るわけではない。監査された形状において N/K 次元はすでにアライメントされているため、任意の次元パディングは実証された主な無駄ではない。タイルの FLOP 削減を主張する前に、生成されたコードと実際のルーティングヒストグラムを検査すること。測定によって優位性が確認された少数の設定を用いる範囲限定の形状ディスパッチャの方が、較正されていない大規模な自動チューニング探索よりも望ましい。

ランクあたりの dense ターゲット QKV は N2304/K4096 を持ち、O は N4096/K2048 を持つ。これら 2 つの射影では量子化への入力が異なるため、一方の量子化を他方に単純に再利用することはできない。ドラフトは BF16 dense であるため、FP8 DeepGEMM に関する結論は適用されない。既存の比較では、テストされた条件下においてデコードの DeepGEMM/CUTLASS MoE は Triton よりも劣ることが判明している。これは Triton が普遍的に最速であることを証明するものではないが、ライブラリ名だけに基づいた置き換えの決定を阻止する根拠となる。

FA3 のソフトマックス、causal/page マスク、スケールの解釈、およびスコア/出力のアキュムレーションは必須の計算である。利用可能な根拠からは、FA3 内部の不要な計算、冗長なアテンション行列の実体化、あるいは有益な split-K/persistent スケジューリング変更は特定されていない。アテンションコアの書き換えは、実証済みの最適化ではなく、プロファイル測定を必須条件とする調査研究として扱うこと。

## 根拠の限界と合否基準

過去のターゲット相当のリプレイには 2546 個のデバイスカーネルが存在するが、ホスト側ではグループ化されたグラフ投入しか確認できない。カーネル実行時間の単純な合算値は、クリティカルパスへの寄与度を示すものではない。このトレースは旧ノード/自動プレフィルおよび stop_profile_failed を使用しており、現在の CUTLASS プレフィルカーネルの優劣を評価することはできない。テレメトリ単体からでも、レイテンシ、計算、または帯域幅の具体的なボトルネックを特定することはできない。今回確認できた既存データには、現在のエキスパートルーティング分布、HBM バイト数、レジスタスピル、アテンションコアの効率性を判断できる情報がない。

高コストなカーネルプロジェクトに着手する前に、設計の優劣を識別できる測定値のみを取得すること: 現在の個別の P/D/draft-extend/検証フェーズのトレース、実測/キャプチャされた行数およびエキスパートごとのカウント、選定されたカーネルのレジスタ/スピル/占有率、Tensor 命令およびメモリトラフィックのデータ、コレクティブ通信の到達および露出した転送時間。最終スコアにはプロファイリングを行わない同一条件の実行を用いること。影響を受ける過去の合算値には KV キャスト/格納 0.559589ms、QKnorm+RoPE 0.344810ms、SiLU+量子化 0.290988ms が含まれるが、これらはより広範な融合設計と重複しており、独立した予測ゲインとして加算することはできない。

AISimulate/DynoSim はキューイングや仮想的なサービスレート変化の検討には依然として有用であるが、新規 CUDA カーネルの正確なタイミングを評価するものではない。現在の CPU 結果では chunk8192 を維持した c44、次いで条件付きの c48 が候補に残っているが、4P/12D は固定 c40 において必要とされる約 1.8〜2.0 倍のプレフィルレートの根拠が依然として不足している。これらサービング側の変更は別個の要因である。カーネルマイクロベンチマークのゲインとシミュレータの goodput ゲインを掛け合わせてはならない。

実装順序: (1) 既存の SiLU 融合、ドラフトヘッドの行刈り込み、およびキャスト/スキャッターのための範囲を限定した個別ブランチ、(2) 互換性のあるセマンティクスを備えたグラフバケットおよび貪欲法交換、(3) プロファイル主導のプレフィルパッキング/down-combine およびデコードエキスパートスケジューリング、(4) 先行する測定によって正当性が示された場合にのみ、より広範なプロデューサー/コンシューマおよびコレクティブ通信の融合を実施。ソースの変更には追跡可能な新規ビルドが必要であり、ランタイムのみの変更では測定済みのイメージを再利用する。ソースミラーは読み取り専用に保ち、所有リポジトリ/承認されたブランチワークフローで実装すること。すべての仮説的候補を試し尽くすのではなく、再現性のあるゲインなし、または SLA の低下が確認された時点で中止すること。

合否判定基準は、モデル/検証セマンティクスが変更されない標準レベルの数値品質、公式入力・同一条件での再現可能な goodput 向上、90% 以上のリクエストにおいて TTFT ≤ 3000ms かつ平均 ITL ≤ 20ms の双方を満たすこと、ならびに Actions/スケジューラ/パーサー/成果物収集の完了である。カーネル単体の実行時間や数値テキストの不一致のみを採否基準としてはならない。主催者による独立した精度チェッカーは要求されておらず、主張もされていない。
