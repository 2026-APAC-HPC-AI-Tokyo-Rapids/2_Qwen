# 2026-10-25 10,000 goodput tok/s へのロードマップ（改訂 3）

起点は **8922.77 good output tok/s**（[40116925551](https://github.com/2026-APAC-HPC-AI-Tokyo-Rapids/2_Qwen/tree/public-actions-history-20261115/40116925551)、`6f0164d`、image 40064516380、c240、Decode 上限 160）。目標 10,000 は **+12.1%**。

改訂 3 の差分。

1. **P1 を rules 上クリアとして扱う**（ユーザー判断）。ただし **bytes の収支を計算すると、Claude Code で議論した「FP32 で合算して 1 回だけ丸める」形は Prefill では 2〜4 倍の負け**になる。rules ではなく算術の問題である。§4 で根拠を示し、**scratch を使わない等価手段（局所性配置）に置き換える**。
2. 改訂 2 で「最大の未回収項」とした **Prefill の clock 仮説を実測で棄却した**（§6.5）。既存 profile の worker 別カーネル時間から、Decode 併置による Prefill の clock 低下は **0.5% 以内**で存在しない。電力・clock は回収不能として計画から外す。
3. その結果、**10,000 は Prefill の kernel 改善だけで作るしかない**。山は **FA3**（42 ms、peak の 39%）と **小 kernel**（19.6 ms）。

## 0. 要旨

- 系は **Prefill 供給 46.5 req/s と Decode の SLA 容量 48.7 req/s で釣り合っている**。**Prefill だけ速くすると 9,350（+4.8%）で飽和し、Decode だけでは 0%**。
- 10,000 の必要条件は **Prefill ≤ 233 ms かつ Decode cycle ≤ 33.9 ms**（§2）。
- **Prefill が唯一の硬い壁**。Decode は 33.9 ms を割れば十分で、それ以上速くしても 10,000 には寄与しない。
- 見込みは **9,470（悪い側）／9,830（中央値）／10,210（良い側）**。**10,000 は FA3 が −8 ms 以上に振れ、かつ小 kernel と配置が中央値以上で着地したときに届く。**
- 電力・clock の回復は **測定の結果、存在しない**（§6.5）。他に大きな 1 手は無い。

## 4. P1 の判定: rules はクリア、しかし bytes で負ける

### 4.1 同定

P1 は Claude Code session `5abe09c0` の 2026-10-24 の議論（「FP32 の部分和を 1 回だけ BF16 に丸めて送る方式」）を指す。expert を持つ rank 上で、同じ token の expert 出力を FP32 で合算し、送信時に 1 回だけ BF16 に丸めることで、remote 行を最大 8 → 最大 4 に減らす案。丸め位置が規則上「演算順序の変更」に当たるかが争点だった。

ユーザー判断により **rules 上は許容**として扱う。BF16 への丸め回数は現行（最大 8）より減るため、精度の方向も悪くない。

### 4.2 bytes 収支（Prefill、4032 token/rank、EP4、top-8、1 層あたり）

| 項目 | 行数 | bytes |
|---|---:|---:|
| この rank が計算する expert 出力 | 32,256 | 264 MB |
| └ 自 rank の token 向け（local） | 8,064 | 66 MB |
| └ 他 rank の token 向け（remote write） | 24,192 | **198 MB** |
| combine が読む量（local ＋ 受信） | 32,256 | 264 MB |

P1 で減るのは remote の 198 MB が半分になった分だけ。

- **節約**: remote write 99 MB ＋ combine read 99 MB = **198 MB/層**。
- **必要になる作業領域**: 合算するには 2 本の出力をどこかに実体化する必要がある。FP32 なら 24,192 行 × 16 KB = **396 MB の write ＋ 396 MB の read = 792 MB/層**。BF16 に落としても **396 MB/層**。
- **収支**: 792 / 198 = **4.0 倍の負け**（BF16 でも 2.0 倍）。

Prefill は token 数が 4032/rank と多いため、作業領域が保存量を必ず上回る。Decode（128 token/rank）なら作業領域は 1/30 になるが、Decode の FC2 は 1 step あたりの絶対量が小さく、律速も重み読み出し側である。

これは推測ではなく、同じ形を serving で試した [39355994503](https://github.com/2026-APAC-HPC-AI-Tokyo-Rapids/2_Qwen/tree/public-actions-history-20261115/39355994503) が **MegaMoE +13%（1682 → 1904 µs）、score −5.8%** だった実測と一致する。当時の敗因は「1.25 GB の symmetric buffer、行ごとの acq_rel atomic、spill 20→112 B」と記録されているが、**staging をどれだけ賢くしても 2〜4 倍という比は変わらない**。

### 4.3 結論

**P1-literal は実装しない。** rules がクリアでも、bytes が増える実装は前回と同じ結果になる。代わりに、**同じ「remote 行を減らす」目的を scratch ゼロで達成する P1' を置く。**

### 4.4 P1'（代替）: 局所性を目的にした expert 配置

remote 行数を減らす方法は、送信をまとめること以外に **「同じ token の expert を同じ rank に置く」** ことでも達成できる。

- 配置は静的で、冗長 expert は同一重みなので **出力は bit 一致**。丸めの順序も変わらない。
- 作業領域はゼロ、カーネル変更もゼロ。**JSON の差し替えだけ**。
- 既に仕組みがある: `configs/firmus-prefill-replica4-expert-location.json` は 140 physical slot に 128 logical expert を割り当て、hot 4 expert（58/11/17/60）を 4 回ずつ複製している。`megamoe-prefill-replicas.patch` と `--init-expert-location` で serving に載っている。
- 「負荷均等」を目的にした最適化は既に成功している（rank 負荷 max/mean 1.338 → 1.034）。**目的関数を「負荷均等＋remote 行数最小」に変える**だけ。

**必要なデータ**: token の rank ごとの expert 割当数。既存の dump（`39051152456`）は 4 EP rank を合算した `(2048, 94, 128)` なので rank 軸が失われている。**1 回の統計 run（recorder 有効、score は比較に使わない）で rank 別に取り直す**必要がある。解析自体は numpy の CPU 仕事。

**見込み**: remote 比率を 6/8 → 5/8〜4.5/8 に下げられれば **−20〜−50 µs/層 = Prefill −1.9〜−4.7 ms**。NVLink 圧が下がる副次効果（D1 で観測した FC1 TMA 競合の緩和）も期待できる。

配置最適化は「32 expert/rank の容量制約下での min-cut」であり、4/8 まで下げられる保証はない。**まず統計を取って上界を計算し、−2 ms に満たなければ捨てる。**

### 4.5 採らない派生

- **DSMEM/cluster で合算**: 1 cluster は最大 16 CTA、expert は 32。token の 2 local expert が同一 cluster に入る確率は約 10% で効果が薄い。
- **BF16 での pair 合算**: 丸め回数は増えないが、作業領域が保存量の 2 倍で負け。
- **受信側の変更**: 受信側は既に 8 行を FP32 で合算しており、送信側が 8 行送る限り削れない。

## 5. Prefill トラック（261 → 233 ms、−28 ms）

**10,000 の成否はここで決まる。** 大きな 1 手が無いので、独立な 6 つを積む。

### P2. FA3 の 4k-causal 専用化（最重要・最大の伸びしろ）

- **根拠**: 450 µs/層で peak の 39%。**この 39% は他のどのカーネルよりも異常**（MegaMoE は 54%、dense は 81〜83%）。Decode 側では同じ FA3 を p128split3 にして 88.3 → 68.1 µs（−23%）を達成しており、同種の手法が Prefill に未適用。contiguous-KV extend で 492 → 450 µs までは来ている。
- **案**: 4096 token/rank・causal・FP8 Q/KV に固定した tile と split を選ぶ。varlen のままだと CTA あたりの work が揃わず、split-KV の combine が固定費になる。
- **見込み**: 450 → 330〜400 µs/層 → **−5〜−12 ms**。Codex は +6〜9%、Fable は +1.4% と見ており不確実だが、**この項の振れ幅が 10,000 の可否を決める**。
- **gate**: balanced-4096 と real43 の両方で control 比 −5% 以上。−5% 未満なら Phase 2 で方針を再決定する（§9）。

### P3. 小 kernel の融合（第 2 位）

- **根拠**: 208 µs/層。qknorm/RoPE 66 µs は HBM の 36% しか使っていない。add + RMSNorm + group quant + pre-dispatch も 2 パス。
- **案**: ①add + RMSNorm + group quant + pre-dispatch を 1 pass、②qknorm + RoPE + FP8 Q を 1 pass。既存 patch の延長で、新しい量子化点を足さない。
- **見込み**: 208 → 130〜160 µs/層 → **−4.5〜−7.3 ms**。bit 一致を要求できる。

### P1'. 局所性配置（§4.4）

- **見込み**: **−1.9〜−4.7 ms**。bit 一致、カーネル変更なし。

### P4. rank 間の速度差を見込んだ配置

- **根拠**: 2 WG timeline で rank 2/3 の mainloop が同じ block 数で約 5% 遅く、combine 前の待ちが rank 0 で 75 µs、rank 2/3 で 12〜16 µs。速い rank が遅い rank を待っている。
- **案**: P1' と同じ最適化の制約に「FLOP/rank の均等」を入れ、P1' と同時に解く（別々に解くと衝突する）。
- **見込み**: **−1.9〜−3.8 ms**。
- **注意**: この観測は 1 node 4 GPU の bench。2 node 8 GPU の serving で再現するかを B1 のログで確認する。

### P5. D5a（padding 行の WG 省略）と dispatch 削減

- **根拠**: D5a は実 routing で −0.4〜−1.8%、bit 一致、実装・compile・pytest 済み（`8b7d984`）。dispatch は 25 µs/層。
- **見込み**: **−0.8〜−2.4 ms**。手間がほぼゼロなので同乗させる。

### P6. dense GEMM の残り

- **根拠**: 効率 81〜83%、約 560 µs/層。余地は小さいが 5% で −2.5 ms。
- **見込み**: **−1.2〜−2.5 ms**。他項の build に同乗させるだけ。

## 6. Decode トラック（36.3 → 33.9 ms 以下、−2.4 ms 以上）

Decode は「33.9 ms を割れば十分」なので、**D1 単独で要件を満たす**（最悪側で 33.9 ms）。D2・D3 は余裕のための保険であり、score への寄与は小さい。

### D1. Decode MegaMoE の供給側再設計（要件を満たす本命）

- **根拠**: 218 µs/層 = step の 56.5%、重み HBM 床 126 µs に対し帯域 58%。独立 WG 化（C）で既に −2.3%。
- **案**（`research/runtime-performance/2026-10-23-decode-126us-design.md` の A/B/D を C 適用後の形で）:
  - **A**: dispatch の件数集計を 132 CTA × 128 expert = 16,896 atomic から、小さい prepare 1 回へ。目標は起動→FC1 を 19 → 8 µs。
  - **B**: FC1 の FP32 全量 staging（16 KiB）を register 保持＋部分 amax 交換（2 KiB）へ。前回 B が負けたのは amax 交換を入れず register を増やしただけだったため、同じ形は繰り返さない。
  - **D**: FC2 を出力 chunk 順に並べ、chunk が揃った順に combine する。
- **見込み**: 218 → 180〜190 µs/層 → **−2.4〜−3.6 ms**（step 32.7〜33.9 ms）。要件をちょうど満たす。
- **gate**: まず compile と SASS（spill 0、WGMMA 直列化 warning なし）。C で 8/8 B の spill が残っている。

### D2. verify attention の再設計（余裕を作る）

- **根拠**: 74.8 µs/層（FA3 verify 69.5 + combine 5.3）で KV 床 35 µs に対し 50%。p128split3 で 88.3 → 68.1 µs を取っている。
- **案**: split の partial を global に書いて combine する 2 段をやめ、1 CTA 内で FP32 累積して LSE を 1 回で合成する。
- **見込み**: 74.8 → 55〜60 µs/層 → **−1.4〜−1.9 ms**（step 31.3〜32.5 ms）。

### D3. EAGLE 受理長 2.21 の切り分け（安価・情報量大）

- **既に測れていること**: accept 2.211 は PD 経路の Decode worker の server state（4 DP state すべて 2.2103〜2.2115）と 499 サンプルのログで一致する。**測定誤差ではなく、経路の実力値**。
- **残る問い**: これが「PD 経路の欠陥」か「入力（Shakespeare 風）の性質」か。nebius の model card は K=7 で 4.25〜4.32 としており、同じ重み・同じ draft で 25〜30% 低い。
- **案**: 玄界の 1 GPU で **PD を使わない**単一サーバーに一般的な prompt 30 本を流し、K=1〜7 の τ(K) を測る。`1ebd7e7` の `prepare-eagle-accept.sh` が既にある。Firmus のノードは使わない。
- **判定**: τ(4) ≥ 2.5 なら PD 経路を疑う。τ(4) ≈ 2.2 なら入力起因で、この項は閉じる。
- **位置づけ**: accept が伸びても Prefill の壁は動かない。**10,000 の必須条件ではない**ので、Phase 1 の空き時間に 1 GPU で流すだけにする。

### D4. 設定（cap / K / concurrency）

- K=2 + cap192 は step −7% / accept −9% で中立。**Prefill が 53 req/s を超えた後**に再評価する。
- concurrency 240 → 210 は開始一斉投入の TTFT 不合格を狙うが、8793.13（c240、97.59%）と 8854.80（c240、97.37%）、c192 の系（94.9〜96.2%）を見る限り **c と good 率の相関は弱く符号も不明**。単独 run を割かず、束ねた run の一要素として 1 回だけ試す。

### Decode 合計

D1（−2.4〜−3.6）＋ D2（−1.4〜−1.9）で **31.3〜33.9 ms**。要件（33.9）を満たす。

### 6.5 電力・clock 仮説の検証結果（棄却）

改訂 2 では「node B で Prefill 4 GPU と Decode 4 GPU が電力予算を共有し、Prefill が 1.38〜1.40 GHz に絞られている。Decode の電力を下げれば Prefill が戻る」という仮説を最大の未回収項に置いた。**既存 profile で棄却できた。**

`40071892077` の `kernel-summary.json` は worker ごと・device ごとのカーネル時間を持つ。node A（prefill-0/1、8 GPU）と node B（prefill-2＋decode-0）の Prefill を、1 カーネルあたりの時間で比較する（device 4 枚の平均）。

| worker | node | 同時に走るもの | 1 カーネルあたり | device 間の幅 |
|---|---|---:|---:|---|
| prefill-0 | A | Prefill 8 GPU | **173.20 µs** | 172.94〜173.48 |
| prefill-1 | A | Prefill 8 GPU | **173.94 µs** | 173.85〜174.17 |
| prefill-2 | B | Prefill 4 ＋ Decode 4 | **173.98 µs** | 173.65〜174.18 |

**node の違いも Decode の併置も説明変数になっていない。** prefill-2（Decode と同居）は prefill-1（同居なし）と 0.02% 差、node A 内の prefill-0 と prefill-1 の差（0.43%）のほうが大きい。worker 間のばらつきは 0.5% 以内に収まっている。したがって

- **Decode の電力を下げても Prefill の clock は戻らない。**
- 1.38〜1.40 GHz は、8 GPU/ノードで FP8 を持続稼働させたときの定常値であり、**スケジューリングで回収できる余地は無い**。
- bench（1 node 4 GPU）の 1.47〜1.67 GHz は、GPU 数が半分で持続時間も短い条件の値であり、serving と直接比べてはいけない。

`nvidia-smi -lgc` の可否を確認する価値も無い（下げても効果が無い）。**この項は計画から外す。**

## 8. 判定プロトコル

run 間ばらつきが ±3% あるため、素の score 比較では +12% の判定ができない。以下を固定する。

1. **bench の合否は µs/層**。control を同じ allocation の末尾で再実行し、その差 ±0.3% を超える改善だけを採用候補にする。
2. **serving の比較は直前 bundle との対比**で、score と raw 要求数が同じ向きに動くことを要求する。
3. **台帳を必ず取る**: Prefill 1 iteration ms、Prefill token/rank、Decode step ms（ITL×accept）、running/rank、accept 長、Prefill/Decode の clock。**採否は score ではなく台帳で説明できたときだけ確定する。** clock は §6.5 のとおり操作できないが、run 間の差を他項の効果と誤認しないために記録する。
4. score の正本は `/srv/qwen-artifacts/<run>/1/results/results/score.json` と Actions summary。**保管ジョブの `needs.firmus.result == 'skipped'` を再導入しない**（過去に 6 run の回収が漏れた）。
5. 10,000 の主張は **適格な run 2 回の連続**で行う。
6. profile と bench は分離する。profile 付き run の値は採否に使わない。

## 9. リスクと撤退条件

| リスク | 影響 | 対処 |
|---|---|---|
| P2 の FA3 が −5% に届かない | −2 ms 止まり。**10,000 が届かない** | Phase 1 の出口判定で方針を再決定。無駄な Phase 2/3 を打たない |
| P1' の上界が −2 ms に満たない | −2〜−5 ms を失う | Phase 0.3 の CPU 計算で先に判定。GPU を使わない |
| P3 の融合が register/帯域で失敗 | −4〜−7 ms を失う | bit 一致 gate と compile/SASS を先に通す |
| P4 の skew が serving で再現しない | −2〜−4 ms を失う | B1 の Prefill ログで rank 別 seq 数を確認してから配置を作る |
| D1-B で register が溢れる（C で 8/8 B の前例） | Decode が 33.9 ms を割らない | compile/SASS を先に gate。溢れたら A と D だけで進む |
| run のばらつき ±3% | 10,000 の判定がぶれる | §8 の 2 回連続要求 |

**撤退条件**: Phase 1 の KB1 で **P2 が −5% 未満**、または Phase 2 の B1 で **Prefill が 242 ms を切らない**場合、10,000 は現行 16 GPU・P3/D1 では届かないと判断する。その時点で
(a) 到達点（おおむね 9,500〜9,800）を確定値としてまとめ、Prefill の次の山（MegaMoE の FC2 出力を NVLink ではなく同一ノードの SMEM で閉じる再設計、または Prefill 4 worker 化）を別 campaign として切り出す、
(b) D3 が当たった場合に限り、Decode の余力で cap を上げて 9,800 前後を狙う、
のいずれかとする。**P:D 13:3 は TP4 単位では 3 GPU worker が作れないため、EP3 Decode の実装が前提**であり、本 roadmap の範囲外。

## 10. 決定が必要な事項

1. **P1-literal を落とし、P1'（局所性配置）に置き換えることの承認**。§4.2 の bytes 収支が根拠。rules は既にクリアなので、判断は「4 倍損な実装を試すか、scratch ゼロの等価手段に切り替えるか」である。
2. **Phase 1.4 の統計 run（recorder 有効）を 1 回使ってよいか**。P1' の上界計算に必須。score は比較に使わない。
3. **Phase 1 の出口判定を「P2 −5%」に置いてよいか**。ここで止めれば、届かないと分かっている Phase 2/3 に 3 run を使わずに済む。
4. **B1 の合格線を Prefill 238 ms とするか 242 ms とするか**。238 ms なら Phase 3 に進む前提が揃い、242 ms なら 10,000 は P2 の上振れ頼みになる。
