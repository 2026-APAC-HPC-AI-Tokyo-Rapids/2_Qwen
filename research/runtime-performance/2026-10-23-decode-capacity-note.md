# Decode容量の検討メモ（2026-10-23）

当時の観測に基づく見積もりと提案を保存したものです。本文の改善見込みは通常servingで確認済みの結果として扱いません。後続の測定・採否は [kernel theory tracker](kernel-theory-tracker.md) と [提出結果の来歴](../../submission/EXPERIMENTS.md)を参照してください。

はい、kernel を 1 つずつ削る方向は頭打ちに近いです。最近の 3 回は、+1.5% → 0% → +1.0% でした。ただ、方向を変えれば +15〜25% を狙える大きな手が 1 つ残っています。Decode が 1 step で処理する要求数を増やす方向です。

**今の上限の構造**
- スコアは Decode の容量で決まっています。1 rank が 32 要求を 31 ms の 1 step で進め、1 step で平均 2.2 token 出ます。4 rank 分の上限は約 9,100 tok/s で、今の 8,577 はその 94% まで来ています。
- 残りの kernel を理想まで縮めた場合の上限も計算しました。

  | kernel | 今（1 層） | 下限 |
  |---|---:|---:|
  | MegaMoE | 200 µs | 126 µs |
  | FA3 | 46 µs | 29 µs |
  | dense GEMM | 30 µs | 15 µs |

- これがすべて達成できれば step は約 40% 短くなりますが、現実には 1 回の改善で 1% 前後ずつで、L2 先読みのように効かない手も増えてきました。

**残る大きな手：1 step の要求数を増やす**
- MegaMoE は重みを読む時間で決まっていて、token 数を増やしても時間がほとんど変わりません（4 token で 126 µs、128 token で 196 µs）。1 step に詰める要求を増やせば、重みを読む費用を多くの token で割れます。
- それでも上限を 128 から上げられないのは、128 行を超えると次の 2 つの崖があるからです。
  - **FA3：** 34 要求/rank 以上で処理が 2 巡になり、約 46 → 80 µs に跳ねます。
  - **MegaMoE：** 144 token を超えると、速い SwapAB の経路から外れます。今の 128 では約 200 µs で、遅い経路では 229 µs 以上です。
- このため、cap 132 は −2.4% でした。今の kernel のまま 160 や 192 に上げても、計算上はほとんど得になりません。

**崖を消した場合の見積もり（上限 192 = 48 要求/rank）**

| 1 層あたり | 今（128） | 192 で崖あり | 192 で崖なし |
|---|---:|---:|---:|
| MegaMoE | 200 µs | 約 240 µs | 約 205 µs |
| FA3 | 46 µs | 約 90 µs | 約 69 µs |
| dense GEMM | 30 µs | 約 40 µs | 約 40 µs |
| その他 | 約 53 µs | 約 62 µs | 約 62 µs |
| **step の伸び** | — | ×1.31 | **×1.14** |
| 要求数 | — | ×1.5 | ×1.5 |
| Decode の容量 | — | +15% | **+32%** |
| ITL 平均 | 14.2 ms | 約 18.6 ms（SLA の 20 ms に近く危険） | 約 16.2 ms（p99 も 19 ms 前後に収まる見込み） |

Decode の容量が増えると、今度は Prefill が律速になります。Prefill には今、待ち行列が空の時間が 4〜5 割あるので余力はありますが、無限ではありません。**現実的な見込みは +15〜25%** です。

**そのために必要な作業**
1. **FA3 の split 版を直す：** 今回作った split 2/3 は数値検査に落ちました。原因は空の split の扱いなど、作りの不具合と見ています。直れば、48 要求でも時間が要求数にほぼ比例して伸びるだけで済みます。
2. **MegaMoE の SwapAB を 192 token まで広げる：** 144 まで広げた host patch の延長ですが、tile の形を変える必要があるかもしれません。
3. **設定：** 上限 192、concurrency 260〜290、Decode の CUDA graph のサイズを 48 まで、KV 容量を見直します。KV 容量は rank あたり 98k token あるので、足りる見込みです。

提出は image build 1 回 → serving 1 回にまとめられます。FA3 の版は、今と同じく job の中で選びます。ただし上限は job の中で選べない設定なので、kernel が見込みどおりに速くならなければ、その run のスコアは下がります。
