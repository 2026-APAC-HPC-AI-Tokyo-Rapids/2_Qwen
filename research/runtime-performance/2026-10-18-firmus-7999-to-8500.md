## 3. 定常状態は Prefill の供給量で決まっている

開始後 20〜115 秒の 95 秒間を定常区間とした。
client の開始・完了はともに 41.6211 request/s、first-token ack は 41.6105 request/s。
時間積分した実行中 request は 191.87、うち first token 前 76.01、first token 後 115.86 だった。

同じ区間のサーバーログでは、Prefill の全 12 rank が一回に新規 1 request、4032 padded token を処理する。
保存済み全入力の chat template 適用後の長さは、3994 tokenが12747件、3995 tokenが53件である（`input-length-counts.json`）。
以下のprofileの代表形状とCPUの128件の速度標本は3994 tokenで、どちらの長さも4032にpaddingされる。
worker ごとの一 rank あたり batch 数は 331、329、328、計 3952 request / 95 s = 41.6 request/s で、client 側と一致する。
各 rank の待ち行列は平均 3.58〜3.70、合計約 43.6 request。
bootstrap/optimistic queue は 0、inflight は 1、cached token は 0 だった。
全 rank の batch 数も worker 内で一致しており、今回の定常区間で idle rank 用 geometry が主因になっている形跡はない。

Decode の各 rank は平均 29.59〜30.03 request を処理し、32 request の上限にいるログ標本は約 13〜17%にとどまる。
`#queue-req` は合計平均約 0.46、retraction は 0。
40 iteration ごとのログ間隔から求めた cycle は約 31.33〜31.42 ms、平均 acceptance は 2.214〜2.227 token/iteration。
ログ時刻は秒単位なので、cycle の小数点以下までを精密な計測として扱わない。

`#transfer-req` は合計約 61.9、うち prealloc は約 8.9 request だが、これは通信中の byte 数や NIC 待ち時間ではない。
Prefill の計算待ちを含む状態数なので、61.9 × latency をネットワーク転送コストに換算してはいけない。
client と scheduler の active 数も計測点・状態定義が異なり、115.9 と約 119.2 の差を異常とは判定しない。

現状の ITL からの粗い Decode capacity は `128 / (199 × 0.01397) ≈ 46.0 request/s`。
target の 44.23 request/s は約 123 request の同時 Decode に相当する。
batch が増えれば cycle 自体も伸びるので保証値ではないが、**最初から Decode cap を増やす必要性は示されていない**。
Prefill を改善した後に、cap128 のまま Decode queue と ITL の変化を見るのが妥当である。

## 6. 約 17 ms を削る候補

### A. QK-norm/RoPE/FP8 の仕事の割り当てを再検討する

既に norm、RoPE、FP8 Q、FP8 KV store は融合済みで、同じ fusion を新しい改善として数えない。
profile 全体の当該 kernel 平均は worker 0/1/2 で **152.32 / 152.57 / 154.42 µs/層**。
過去の small-kernel 文書の 45〜55 µs は帯域からの未計測見積もりで、今回の実測は達していない。

現在の Prefill は `head_groups=4`、4 warp/CTA、chunk=6 で、1 warp が 68 head 中 17 head を処理する。
同じ warp 内で norm の reduction と RoPE を多数繰り返す構成になっている。
まず `G=8/chunk=4`、`G=12/chunk=6`、`G=16/chunk=4` の少数候補を、現在の `G=4/chunk=6` と比較する。
一 head の lane 配置、二乗和の加算順序、BF16 丸め、FP8 変換、slot 0 の扱いは変えない。
変更するのは head を warp に割り当てる方法で、出力の byte 一致を採用条件にできる。

仕事を細分化すれば norm weight や cos/sin の再読込と CTA 数が増えるので、速くなる保証はない。
register/occupancy、serial reduction、load/store 命令数、I-cache のどれが支配的かは現在の nsys だけでは分からない。
それでも、変更が小さく、約 14.25 ms の対象時間が実測されているため、検証費用に対する優先度は高い。
仮に半減できても短縮は約 **7.1 ms**で、これ単独では 8500 に届かない。

### B. Prefill attention に連続 FP8 K/V を渡す

現在の profile の FA3 kernel は、FP8、causal、varlen、**PagedKVNonTMA=true、PackGQA=true、Split=false** の 128×160 tile。
SGLang の CMake が固定する [sgl-attn f89bc230 の dispatch](https://github.com/sgl-project/sgl-attn/blob/f89bc2306632d1ec5f97b014dded4254f5b4a907/hopper/flash_api.cpp) と照合した。
TMA 経路の選択には page size が選択される N tile の倍数である必要があり、FP8・head_dim128 の非 paged 経路では N=224。
**page size 64 を 128 や 256 にするだけでも、この条件は満たさない。**
また NonTMA 経路では `pack_gqa=False` を渡しても template の条件で true に戻る。
現在 Split=false なので、`num_splits=1` を指定するだけの改善も期待しない。

今回の Prefill は cached token 0、全 prompt を一回で処理する。
そこで、QK-norm/RoPE/FP8 kernel が paged cache と同じ値の **連続 FP8 K/V scratch** も出力し、target の Prefill attention には `flash_attn_varlen_func` で直接渡す案を優先する。
paged KV への書込みは後続の PD 転送に必要なので残す。
scratch は layer 間で再利用でき、追加の出力 payload は `2 × 3994 × 4 × 128 ≈ 4.09 MB/層`。
94 層分を同時に保持する必要はない。

この変更は、paged-KV 読出しと強制 PackGQA を避ける構造的な候補である。
128×224 の TMA 経路を使える可能性があるが、FA3 の速さや追加 write の費用は GPU で測るまで分からない。
対象は約 **45.88 ms**なので、20%短縮できれば約 **9.18 ms**になる。
これは達成予測ではなく、8500 に寄与するための目安である。

実装時の条件は次のとおり。

- full Prefill、prefix 0、対象の FP8 scale/layout の場合だけ選択し、chunked/cached/decode は既存経路に残す。
- 既存 kernel は fused store 時に BF16 K を更新しないので、その BF16 K を直接 attention に渡してはいけない。
- 3994/3995 real token と 4032 padded token を区別し、cu_seqlens と tensor 行数を一致させる。padding を実 request の attention 範囲に入れない。
- paged と scratch の FP8 Q/K/V の値を一致させ、attention 出力を FP32 参照と既存 FA3 の両方に対して検証する。
- KV store の完了順序、PD 転送、EAGLE aux/draft、replay 時の buffer lifetime を保持する。

単に embedding 用の `fa_skip_kv_cache` を有効にする方法では、FP8 scale の条件と PD 転送の要件を満たさない。
これは今回まだ実装していない kernel/attention 改善案である。

### C. 既存の追加 bundle を重複して見積もらない

別作業の commit `a7b9edd103906a1297718412ee374d89b01dc145`、[Actions 39119219065](https://github.com/2026-APAC-HPC-AI-Tokyo-Rapids/2_Qwen/tree/public-actions-history-20261115/39119219065) には、input norm+quant の復帰、flat barrier の拡張、SwapAB threshold 144 などがある。
調査時点では実行中で、今回の作業では開始・停止・変更していない。
7999 baseline に入っていない分だけを今後の候補に数える。

input norm+quant の fusion は 94 層すべての norm/quant を消す変更ではなく、residual、EAGLE aux 取得層などの条件もある。
norm 全体 5.90 ms と quant 全体 3.73 ms をそのまま削減量にしてはいけない。
この候補に期待するのは不足分の 1〜2 ms 程度を測定で確認することで、単独で 8500 を達成する根拠にはしない。
以前の数値 gate に関わる変更なので、baseline と同じ精度条件での検証が必要である。

### D. MegaMoE と dense GEMM

MegaMoE は Prefill target の約 161 msを占めるため、10.5%程度短縮できれば約17 msになる。
ただし今回の image は prefetch、tail の dynamic FC2、paired combine、scale の更新削減などを既に含む。
それらの以前の見積もりを再度加算できない。

既存 geometry 調査では、128×256・3 stage・640 thread は shared memory 約225.6 KB、launch bounds の実際の register 上限は96。
4 stage は約275.8 KBとなり容量を超える。
追加 accumulator を使う FFMA 案には1856 B spillとWGMMA直列化の既存証拠があり、優先しない。
128×128、192×128 などの変更も、書込み・padding・warpgroup 数を含めて評価する必要があり、tile 数だけでは改善を判断できない。
static expert redundancy R8 の既存解析は改善上限自体が小さく、8500の中心には据えない。

dense GEMM は約42.8 msで、5%削減でも約2.1 msになる。
QKV projection と output projection を shape 別に分けた tuning は補完候補だが、現 artifact は同じ kernel 名に両方が集計されている。
現在の kernel 時間だけから optimal tile や達成率は決められない。
MoE の新しい大規模な再設計より先に、A/B/C の効果を確認する。

## 7. 8500 に届く条件を数値で置く

定常の nominal throughput は `41.62105 × 200 = 8324.21 tok/s`。
通常 score との比 `7999.36795 / 8324.21053 = 0.960976` を開始・終了等の経験的係数とすると、目標は次のようになる。

```text
required steady request/s = 8500 / (200 × 0.960976) = 44.2259
baseline Prefill ms/request = 12 × 1000 / 41.62105 = 288.3156
target Prefill ms/request   = 12 × 1000 / 44.22586 = 271.3344
required reduction         = 16.9812 ms/request
```

この係数は物理定数ではなく、改善後には TTFT 失敗数、drain、Decode の混雑も変わる。
以下は「同じ係数で、削減時間が critical path にそのまま効く」とした感度分析であり、実測 score の予告ではない。

| 仮定した Prefill 短縮 | 換算 score、tok/s |
|---|---:|
| 2 ms | 8055 |
| QK-norm 系を半減、7.125 ms | 8202 |
| FA3 を20%短縮、9.176 ms | 8262 |
| 上記2つ、16.301 ms | 8479 |
| 17.000 ms | 8501 |
| 上記2つ＋1.4 ms、17.701 ms | 8523 |
| 20 ms | 8596 |

このため、**QK-norm 系だけを高速化して終了する計画では不足する**。
QK-norm 系と attention の両方、または attention/MegaMoE のどちらかでより大きい短縮を得る必要がある。
8500を確約できる証拠はまだないが、削る対象と必要な短縮量はここまで絞れる。

## 9. 次に検証する順序と打切り条件

以下は将来の検証計画で、今回ジョブは投入していない。

1. **gigatokenのみの変更を独立した比較単位に保つ。** CPUで全入力一致を確認済み。新imageを作る際はpackage、patch、全workerのbackendを確認し、公式scoreとTTFTの変化を測る。
2. **QK-norm系の少数候補をH200で比較する。** 同じFP8出力とKV storeのbyte一致を先に確認し、3994/3995/4032 tokenの実形状、Decode小batchも確認する。Prefillで数msにもならないなら深追いしない。
3. **連続FP8 K/Vのattention経路を単独で検証する。** 同じFP8入力と正しいcausal/padding条件で既存FA3と比較し、追加scratch書込み込みの差を見る。attention kernelだけの改善値を採用値にしない。
4. **norm+quant/flat barrierの既存結果を反映する。** 他の変更と同時に改善したrunだけから個別の速度を帰属しない。
5. **合計で約17 msの見通しが立ってから公式E2Eで判定する。** c192、cap128をまず固定。Prefill供給44.2 request/s付近、Decode queue、ITL、TTFT、goodputを確認し、複数回の通常計測で8500超が再現するかを見る。
6. **最後にc176を比較する。** Prefillが飢餓状態にならないことを確認しつつ初期burst/drainの損失を減らす。profileのscoreは採用判定に使わない。

今回のprofileはどのkernelに時間を使うかまでを示す。
QK-normのstall内訳、FA3を連続KVにした際の実効速度、更新後のDecodeのcapacity、公式scoreのrun間分散は未確定である。
それらを断定せず、次の検証で否定できる仮説として残す。
