## P3 の規則と過去データ

P は control 比 5 µs の条件を維持する。P3 は元の入力と変更入力 2 回で attention・scale・O が P と byte 一致する候補だけを対象とする。FP32 参照、single の経路・byte 一致、1200 回耐久、12 UUID の集合と allocation ID、image/binary identity の条件も維持する。

P3 の速度は 12 GPU × 7 形状の 84 cell 全体で判定する。cell の pooled 短縮の中央値が 3 µs 以上、正の cell が 90% 以上（少なくとも 76 cell）、最悪 cell が −3 µs 以上。forward と reverse の cell 中央値の、それぞれ 84 cell を通じた中央値がともに正であること。形状別の中央値や各 cell の order には追加の margin を設けない。byte 一致の候補には数値の危険の取引がないので、採否は平均的に速いことと大きく負ける cell がないことで決める。統計量は指定どおり中央値を用い、算術平均へ置き換えない。

## 候補 A の設計と bit 一致の契約

対象は Qwen の EAGLE3 target verify、Q4、B1〜48、vocab 152064、BF16 logits、greedy。主対象 B44/46/48。LM head の GEMM、全語彙の計算、FA3、MegaMoE、draft GEMM、c232、cap48、steps3/draft4 は維持する。既定の SGLANG_DECODE_GREEDY_VERIFY は 0。

専用 AOT kernel は 4096 列ごとの tile と小さい集約の 2 段。BF16 を FP32 へ正確に展開し、既存 sanitize が有効なら penalty の前に NaN を −1e30、±Inf を ±1e30 へ変換する。同じ FP32 の min-token penalty を加え、全 vocab を比較する。NaN は最初の index、通常の同値最大値も最小 index を選ぶ。penalty によって新しく生じた NaN（例えば +Inf + −Inf）は再 sanitize しない。argmax の int64 token を既存 verify_tree_greedy_func にそのまま渡し、accept 判定の kernel は変えない。

stop token は既存の stop_token_ids、additional_stop_token_ids、eos_token_id の集合そのものを再利用する。ignore_eos によって min-token を省かない。判定は既存と同じ len_output_tokens < min_new_tokens で、Q4 の各行に同じ request の penalty を適用する。overlap が live length を更新しても control の dense penalty と同じ時点を使うよう、length を clone して保持する。filter・幅の異なる stop 集合の merge も追従する。

min-token だけが有効な greedy batch では、毎 step の dense additive / where buffer を作らず stop ID と length の snapshot を使う。初期化時の既存 dense stop table は通常経路との互換のため保持する。他の penalty、bias、grammar、logprob、非 EAGLE3、非 greedy、async assert の経路は通常の FP32 処理を使用する。疎な snapshot を通常経路が使う場合は、同じ dense FP32 演算へ展開する。これは対応する sampling 条件の dispatch であり、実行エラーを隠す retry ではない。

target verify の graph は専用の BF16 logits buffer を DecodeInputBuffers が所有する。draft/non-verify の共有 FP32 buffer と混ぜない。softcap などの通常経路は FP32 を維持する。argmax の partial と output は graph pool または通常 stream の allocator の寿命に従う。replay 内で host の length や penalty を定数として埋め込まない。

必要な比較は約 26.76〜29.20 M/step、penalty の FP32 加算も維持する。LM head の算術量 2×(4B)×152064×4096＝219.245〜239.176 GFLOP/step は不変。既存 penalty broadcast の採用済み利得は今回へ再加算しない。A は新規候補であり GPU での過去の棄却記録はない。FP32 中間は 107.05〜116.79 MB。cast 書込み、penalty 読み書き、argmax 読込みの論理 traffic は約 428.21〜467.14 MB で、融合後の BF16 buffer 読み書き約 107.05〜116.79 MB と小さい partial へ置き換わる。入力 BF16 を buffer に読む仕事は両方に残る。min-token の B×vocab FP32 buffer は 26.76〜29.20 MB/本で、この毎 step の全量生成も減る。HBM に実際に出る量・実効帯域・clock は未測定。NVLink の削減は主張しない。

## CPU の証拠

CUDA と同じ greedy_verify_math.cuh を g++ でコンパイルし、独立した NumPy の BF16 bit 展開 → FP32 sanitize → dense penalty → argmax と照合する。B1/32/44/46/48、全 152064 語彙、padding stride、min-token 前後、複数 stop、NaN の両端・payload、±Inf、全同値、tile 境界 tie、signed zero、BF16 subnormal、penalty なし、入力を戻した状態を検査する。token から同じ verify を使うため index・length・bonus の一致が従うことを CPU 参照でも確認する。実際の GPU verify の一致は GPU gate の責務で、CPU 模型だけで GPU 合格とはしない。

SGLang の pinned commit fc275674a97d78553b22597ee72c8fd48f5420f4 に既存 image/build/runtime overlay を順に適用した 5 ファイルを fixture とし、新 patch の適用・構文と LM head / verify 関数の不変を検査する。mirror は読み取りだけに用いた。

CUDA 13.4、sm_90a、O3、ftz=false、fmad=false で CPU compile。greedy の TU だけ use_fast_math を除外し、subnormal の flush を防ぐ。attention の compile flags は維持する。tile は 31 registers、finish は 32 registers、両方 stack 0、spill load/store 0、静的 shared memory 64 bytes、C75xx 警告なし。SASS は BF16 の整数 bit 展開、FP32 FADD、NaN を含む比較、SHFL、少量の shared reduction で、FP32 中間 logits の store はない。FADD.FTZ と FFMA は使わない。cuobjdump の shared 1088 bytes は compiler/runtime の予約を含み、ptxas の静的 64 bytes と区別する。

正本は decode-greedy-cpu-validation-20261102.json（source/cubin/SASS hash、flags、opcode 数）。Torch 2.11.0+cu130 headers と CUDA13.4 headers に対して新 wrapper の実コードを g++ で構文検査した。image の CUDA 13.0.88 の同等性・library link/load・GPU 実行は未確認。fresh build 内でも greedy の 2 kernel の spill と C75xx を検査し、SASS を build log に保存する。

## Decode gate と時間

P pair/prepack のすべての worker と集約が終了してから、model の起動前に別の srun を実行する。g4 の 8 GPU を短時間予約し、nvidia-smi の物理 index 4〜7 を UUID に解決して torchrun の CUDA_VISIBLE_DEVICES に設定する。計算は Decode の 4 GPU だけ。Prefill の GPU 集合とは別で、host、4 UUID、rank、run ID、image hash、binary hash を照合する。

実際の SamplingBatchInfo.update_penalties、LogitsProcessor の buffer 接続、eagle_sample を両経路で graph capture する。B1/32/44/46/48、padding あり・なし、sanitize あり・なしで、initial、min-token 境界、入力と penalty 状態変更、特殊値、初期入力への復帰を検査し、token・accept index・accepted length・bonus token が完全一致すること。penalty なしの capture も比較する。初期入力への復帰は control との一致だけでなく初回 snapshot とも照合する。

最後に B48 の candidate graph を各 GPU で 10000 回連続 replay。各回の 4 出力の不一致を GPU 上の sticky flag に OR して途中の非決定性も検出する。耐久用検査は性能測定には入れない。

性能は B44/46/48 × padding 両方、全 4 GPU、forward/reverse、各 3 block、5 round、16 replay/標本で、各 order/block の control と candidate の中央値差が 0.05 ms 以上。区間に logits copy/cast、penalty snapshot/準備、argmax、既存 verify、bonus の接続を含む。単独 kernel の速度だけでは採らない。

全員合格の場合だけ candidate env を作り、集約プロセスが正常終了して adopted が真であることを shell で確認してから Decode の serving env を atomic rename する。worker failure、timeout、集約が candidate env を書いた直後の timeout、UUID 不整合は control の 0 を保つ。候補 gate の失敗で通常 serving を止めない。追加の retry はない。

見積もりは cold 起動・capture・検査・速度・10000 回・集約込み 60 秒。worker timeout 85 秒＋kill grace 2 秒＋集約最大 3 秒で全体 90 秒、見積もりの 1.5 倍。実 GPU 時間の実測ではない。

既存 P の READY 434〜449 秒、job 718〜742 秒を基準とすると、742＋追加 gate 90＋新 image 初期化余裕 60＝892 秒（14分52秒）、17分まで128秒。通常見積もりの gate60秒なら862秒、余り158秒。上限の異なる工程を二重に合成して保証とはしない。

gate 開始時は保守的に、既存 P job 全体742秒＋初期化60秒＝802秒を以後の serving と回収用に残し、追加90秒を確保できるときだけ起動する。つまり経過128秒以内が開始条件。P gate が長引いた場合は Decode gate を記録付きで省略し control serving に進む。公式60秒warmup・120秒計測・30秒graceは削らない。この reserve は既存 gate を含む job 全体をもう一度残す保守値であり、短縮した残工程の実測値ではない。

## Decode harness の capture 修正（2026-11-02）

run 41359713062 / Slurm 28179 / image c7804efb は、提供記録では4 rank とも約10秒で capture 中の replay 準備を拒否され、serving は control のまま。source の不正経路は旧 `capture(torch, endurance_step)` → capture 内の `candidate.replay()` → PyTorch `CUDAGraph::replay` → generator の `replay_prologue` → `assertNotCapturing`。warmup の1回目は capture 外なので通り、capture 本体の2回目で拒否される。default generator は常に登録され、RNG increment が0かを調べる前に拒否するので、greedy に乱数がなくても発生する。根拠：[CUDAGraph.cpp](https://github.com/pytorch/pytorch/blob/v2.11.0/aten/src/ATen/cuda/CUDAGraph.cpp#L174)、[CUDAGeneratorImpl.cpp](https://github.com/pytorch/pytorch/blob/v2.11.0/aten/src/ATen/cuda/CUDAGeneratorImpl.cpp#L203)。

`build_graphs` は control / candidate を別々に各1回 capture。`step` 内の update_penalties、logits copy/cast、eagle_sample の greedy 分岐に別 graph の replay はない。boundary / changed / special / restored は入力 storage を変更して既存 graph を replay する。`equal` の synchronize、`timing` の標本末尾の event 完了後に、no_penalty や sanitize 切替で再 capture する。状態変更・normal_ は capture 外。

記録済み `1:0` の states は initial → boundary → changed → special → restored。case 記録は両 sanitize / no_penalty の比較後に書く。問題の耐久 capture は全10 case 完了後、最後の `48:1` を initial / sanitize 有効で再比較した直後にしか到達しない。当該 raw fragment は手元になく、提供された最初の case から最後の key は断定できない。最後が `1:0` なら耐久到達とは整合せず、追加の traceback / fragment 照合が必要。

修正は比較と sticky flag の OR だけを専用 graph に capture し、その外で candidate → 比較 graph を同じ stream で10000回 replay する。control と4出力を保持し、比較 capture で candidate 出力を再生成しない。CPU 回帰3件で元の入れ子の拒否、状態変更・再 capture・両順 timing・耐久で capture 中の prepare / replay / synchronize がないこと、graph と出力 storage の分離、途中1回だけの不一致検出を確認した。

変更は harness・CPU test・本 note のみ。kernel / SGLang patch / image / 判定閾値は不変。provision の既存コピー経路で harness を更新するため image c7804efb を再利用できる。SSH、Actions 操作、scheduler / GPU 投入は行わず、実GPUの成功や時間予算の再測定は未確認。
