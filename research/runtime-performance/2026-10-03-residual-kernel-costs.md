# 選択されたライブラリ内部の残留コスト — 2026-10-03

> 追補訂正：過去に検討された、より広範なFP8 RoPE/storeオーバーレイは、-0.298%の性能結果およびgreedy出力の一致が2/8にとどまったことを受けて、すでに却下されていた。この経緯を踏まえていなかったため、下記の「最有力候補」としての優先度評価は過大であった。ネイティブRoPEを維持する最小限のcast/storeフュージョンは、それとは別個の提案ではあるものの未計測の案に過ぎず、検証済みの高速化ではない。シミュレータによる追試結果はこの優先度評価を上書きするものであり、却下済みのオーバーレイは却下されたままとした上で、4P/12Dに必要とされる遥かに大規模なprefill高速化と、条件付きで得られるわずかなフュージョン効果とを明確に分離している。 [シミュレータによる追加評価](2026-10-03-simulator-kernel-layout-sensitivity.md)。

次期候補として最も有力なのはFP8 KV変換/格納の融合（FP8 KV conversion/store fusion）であり、次いで丸めを維持するSiLU/量子化の融合（preserving-rounding SiLU/quantization fusion）である。得られた証拠は、選択された実装の内部に残存する具体的な中間処理を示しているが、確実なスループット向上や、DeepGEMMに対する普遍的により高速な代替手段を立証するものではない。本調査においてGPUジョブの実行や本番ランタイムの変更は行われなかった。

## 対象範囲と来歴

現在採用されているスタック：prefillネイティブCUTLASS MoE、decode Triton MoE、dense target FP8射影 DeepGEMM、FA3 attention、FlashInfer all-reduce/residual/RMSNorm融合、BF16 dense EAGLE3 draft。TP4/EP1、P2D2、c40、投機 steps3/draft4、FP8 KV。P2D2は8基のprefill GPUと8基のdecode GPUを使用する。ユーザーが意図している非対称な候補構成は **4 prefill / 12 decode** であり、その逆ではない。以前のCPUスクリーニングではGPUでの試行を正当化できなかった。本調査はこのレイアウトを変更しない。

ソースはSGLang `fc275674a97d78553b22597ee72c8fd48f5420f4` に固定されている。過去のトレース `36387126341/1` は、同一のイメージ/ソースおよびdecode構成を使用しているが、ノードが異なり（026/030ではなく009/013）、採用されたCUTLASSではなくauto prefillを使用している。また、そのプロファイリング停止は失敗した。したがって、これは構造的なdecodeの証拠であり、現在のCUTLASS-prefillのタイミング比較や反復的な性能実験ではない。

## グラフが実際に実行しているもの

TPランクごとに、147回のtarget相当リプレイと147回のdraft相当リプレイが特定された。各targetリプレイには、188個のMoE GEMM、187個の融合all-reduce/residual/RMSNormカーネル、2個のプレーンなall-reduce（embeddingおよび最終MoE）、1個のlogits all-gatherを含む、**2546個のデバイスカーネル** が存在する。draftリプレイには74個のカーネル（初回は72個）、6個のプレーンなall-reduce、および2個のlogits all-gatherが存在する。draftはMoEではなく、1層のdense BF16モデルである。steps3では、内部ループは2回のdraft forwardを実行する。最初のトークンはdraft prefillに由来する。ラベルはNVTXからではなく、ソースとシーケンスから推測されたものである。

2回のホスト側グラフサブミッションによって、これらの処理はすでにグループ化されている。188個のデバイスカーネルノードを削減することは、188回のPython/CUDAホスト呼び出しを排除することを意味しない。[CUDA Graph documentation](https://docs.nvidia.com/cuda/cuda-programming-guide/04-special-topics/cuda-graphs.html) はサブミッション機構を説明している。グラフ実行それ自体がこれらの中間処理を排除するわけではない。

Rank0におけるtargetのデバイス実行区間（device-span）の中央値は 20.481 ms、draftは 0.428 ms である。targetグラフのAPI区間の中央値は 3.207 ms であるが、その区間の94.4%は既存のGPU処理とオーバーラップしている。イベント同期の中央値は 8.917 ms で、93.9%がGPU処理とオーバーラップしている。これらは独立して削減可能なコストではなく、GPU時間と合算することは作業の二重計上となる。多数のデバイスカーネルが存在することや、長時間のブロッキングAPI呼び出しが存在することは、いずれもPythonの起動ボトルネックを証明するものではない。

## 測定されたアテンション融合の境界

targetリプレイあたり、rank0、147回のリプレイで平均したカーネル実行時間合計：

| 処理 | デバイス呼び出し数 | 合計実行時間 |
|---|---:|---:|
| QK normalization |94|0.164937 ms|
| RoPE |94|0.179873 ms|
| K and V FP8 conversion |188|0.414556 ms|
| KV store |94|0.145033 ms|
| Query FP8 conversion |94|0.244453 ms|

**KV変換 + 格納（KV conversion + store）は層あたり3カーネルであり、1つにまとめられる可能性がある**。これにより、94層にわたり188個のグラフノードと中間FP8バッファが削減される。影響を受けるカーネルの合計は **0.559589 ms** であるが、変換/格納処理自体は依然として必要であるため、これは予測される削減効果ではない。既存のCUDA fused RoPE/KV-writeパスはBF16 KVを要求し、現在のFP8 KVパスはカバーしていない。スケール処理、丸め、キャッシュインデックス、および無効スロット（invalid-slot）の挙動を維持すること。Queryの変換は別個のものであり、KV変換としてカウントしてはならない。[KV conversion/store](https://github.com/2026-APAC-HPC-AI-Tokyo-Rapids/5_SGLang_Src/blob/fc275674a97d78553b22597ee72c8fd48f5420f4/python/sglang/srt/mem_cache/memory_pool.py#L2298) を参照。

QKnorm + RoPEの合計は **0.344810 ms** であるが、単に既存の融合フラグを有効化するだけでは不十分である。[the candidate path](https://github.com/2026-APAC-HPC-AI-Tokyo-Rapids/5_SGLang_Src/blob/fc275674a97d78553b22597ee72c8fd48f5420f4/python/sglang/srt/models/qwen3_moe.py#L603) は各層でpositionsをint32にキャストしているのに対し、デプロイされたグラフバッファはint64のpositionsを格納している。最大94個追加される位置キャストノードが、削減される94個の算術ノードを相殺する可能性がある。純粋なノード削減を主張する前に、その変換を巻き上げ（hoist）または再利用すること。QおよびKの正規化はすでに融合されている。

## MoEのデータ移動とパディングされた処理量

Target hidden4096、128 experts、top8、intermediate1536/TP4=384、94層（`E=128`, `R=8T`）。以下は **prefill T8192におけるランクおよび層あたりの論理バッファ容量/トラフィック** であり、測定されたHBMトラフィック、ピーク割り当て、経過時間ではない。

| 残存する処理 | 具体的なコスト | 候補と限界 |
|---|---|---|
| CUTLASSが8つのルート用にFP8トークン入力を収集/複製する | 入力256 MiB + スケール8 MiB（元の32+1 MiBに対して） | Gather対応のgrouped GEMM、またはgather/量子化融合。局所性のトレードオフは未測定。Decode Tritonはすでにインデックス付き入力読み取りを使用しており、この実体化を回避している。 |
| BF16 SiLU出力が書き出された後、FP8量子化のために再読み取りされる | 論理トラフィック96 MiB | 現在の丸めを維持しつつSiLUとgroup128量子化を融合する。既存の融合APIは異なる順序で丸めを行うため、単に有効化しても等価であるとは証明されていない。 |
| BF16 down-projection出力が書き出された後、ルート結合によって消費される | 512 MiBバッファ、1 GiBの書き込み+読み取りトラフィック | down出力とtop8結合を融合し、既存のFP32リダクションセマンティクスを維持する。BF16 atomicによる近道はない。 |
| ルーティングのcount/prefix/assignmentスキャン | 2ERの論理ルートインデックススキャン。T8192において論理読み取り64 MiB | ヒストグラム/スキャッターの再構成が有効な可能性があるが、実際のインデックス配列はわずか256 KiBでありキャッシュ可能である。これは64 MiBのHBMトラフィックではない。 |

CUTLASSの既存のcombineは、すでにunshuffle、ルート重み付け、FP32アキュムレーションを融合している。重みの転置はビュー（view）である。大きなバッファは繰り返しのゼロフィルではなく `empty` を使用している。グラフが保持するバッファはリプレイごとにホストから新規に割り当てられるわけではない。2回目の活性化量子化は、エキスパート固有の新たな非線形テンソルを処理するため、冗長ではない。詳細なソース抜粋とバイト計算式は、アーカイブされた `moe/README.md` および `moe/calculations.json` に記載されている。

エキスパートパディングは実際の行列演算を浪費する可能性がある：`P = sum_e ceil(n_e / tileM) * tileM`、オーバーヘッド係数 `P / (8T)`。decode T56 および tileM16 において、全128エキスパートに均等分散したという仮定のもとでは、448行の有用な行に対して2048行のパディングされた行が生じ、**4.571×** となる。これは実測された浪費係数ではない。実際のエキスパートヒストグラムは存在せず、隣接する検証トークンは相関したルートを持つ可能性がある。また、保守的な起動グリッドにはGEMMの前にリターンするブロックも含まれており、起動されたCTA数は実行されたパディングFLOPsではない。これらのパスにおいてK/N次元はタイル分割可能である。

観測されたキャプチャ済みtarget行数は 4, 8, 12, 16, 24, 32, 40, 48, 56 である。実際の稼働リクエスト/マスクが存在しないため、グラフパディングを定量化することはできない。エキスパートパディングとグラフパディングは異なる要因であり、仮定のパーセンテージを加算してはならない。Dense DeepGEMMのスケールバッファアライメントも、GEMM行パディングの証拠ではない。

## 通信：何が依然として必要であり、何が冗長であるか

TP4のノード内リダクションとノード間NIXL KV転送は異なるパスである。187個の融合all-reduceおよび2個のプレーンなtarget all-reduceは、モデルが必要とするTP結合と整合しており、冗長な集団通信（collective）は証明されなかった。融合集団通信の所要時間の中央値は 10.048 マイクロ秒（p99 14.080）、ランク間の開始スキューの中央値は 1.777 マイクロ秒である。所要時間には同期が含まれており、純粋なワイヤ転送ではない。ミリ秒単位のテイルは、典型的な融合集団通信ではなく、プレーンな集団通信で発生する。マッチングは分散イベントIDではなく、リプレイ/順序（ordinal）によって行われている。

FlashInferの融合は、block128 FP8活性化出力ではなく、BF16の正規化/残差出力を出力する。さらなる all-reduce + 正規化 + 量子化 の融合には、カスタムH100パスと、ルーター/残差のコンシューマおよび丸めの慎重な維持が必要となる。既存の量子化通信融合はAITERによってゲート（AITER-gated）されており、すぐに利用可能なH100のトグルではない。通常の3992/8192行のprefillは既存の2048トークンの融合上限を超えている。prefillにおけるall-reduce/normの分離はソースで確認された差異であるが、採用されたCUTLASSのprefillトレースでそのコストを定量化したものはない。盲目的にこの上限を引き上げることは正当化されない。

NIXLの [flattened index builder](https://github.com/2026-APAC-HPC-AI-Tokyo-Rapids/5_SGLang_Src/blob/fc275674a97d78553b22597ee72c8fd48f5420f4/python/sglang/srt/disaggregation/nixl/conn.py#L312) は末尾が `.astype(np.int32)` となっている。int32入力の場合、先行する加算によってすでに連続したint32配列が生成されているため、デフォルトの `copy=True` はそれを複製する。CPUのみの候補である `astype(np.int32, copy=False)` は、テストされたint32/int64入力および128/3992/4000/8192トークンインデックスに対して、正確な値、dtype、および入力エイリアスなし（no-input-alias）を維持した。188リージョンを持つ4000トークンにおいて、80回の交互試行による解析ホスト上の中央値は、int32で配列あたり **2.12844 から 0.94790 ms** へと変化した。int64は 1.94258 から 1.94567 ms のままであった。これは記載されたパスにおける冗長なコピーを証明するものであり、ASPIREにおけるTTFTやgoodputの向上を証明するものではない。本番コードは変更されていない。

名目上のtargetのみ・未キャッシュの4000トークンFP8 KVは、draft/キャッシュ再利用/プロトコルを除き、91.797 MiB/ランク、TP4全体でリクエストあたり 367.188 MiB である。各インデックス配列には752000個のint32エントリ（3,008,000バイト）があり、送信元+送信先の配列合計はランクあたり 6,016,000バイト である。これらは752000回の個別のRDMA呼び出しではない。転送キューのカウントやこれらのバイト計算式から、ネットワーク帯域幅のボトルネックは確立されていない。

## 優先順位と次の証拠

1. **FP8 KV cast/store fusion:** ソースおよび過去のトレースコストが存在する、最も有力かつ境界が明確なデバイス候補。まず丸め/スケール/マスクを一致させ、CPU/静的検査を行った上でのみプロトタイプを作成すること。
2. **SiLU + quantization:** 選択されたMoEパスで共有される。明確な実体化が存在するが、厳密な丸めを維持する必要がある。Prefillの入力gatherおよびdown/combineの融合は、現時点で測定された時間帰属がない、より大規模な開発候補である。
3. **QKnorm/RoPE + shared position conversion:** 単に指定された算術カーネルだけでなく、融合後のグラフ全体を検査すること。
4. **Expert tiling/graph buckets:** タイルサイズを選択したり浪費されたFLOPsを主張したりする前に、稼働トークン数対キャプチャされた行数、およびエキスパートごとのカウントを収集すること。
5. **NIXL redundant CPU copy:** 小さく具体的なソース改善候補。エンドツーエンドのクリティカルパスへの寄与は依然として不明である。

AISimulate/DynoSimはスケジューリング、バッチ/レイアウト、仮想的なサービス時間感度をスクリーニングできる。しかし利用可能なモデルは、カスタムカーネルの正確な速度、ランク間同期、EAGLE3のルーティング、またはこれらの融合における丸めの等価性を検証するものではない。シミュレータの精度を捏造してはならない。既存の証拠は候補を絞り込むには十分であるが、集約されたtok/sを予測するには不十分である。将来承認された測定では、現在のCUTLASS prefillを個別にキャプチャし、draft/verifyフェーズをマークし、エキスパートおよび実稼働対キャプチャ行のヒストグラムを記録し、HBMトラフィック/Tensor Core利用率/オキュパンシーを選択的に検査すべきである。その上で、公式のAIPerfレイテンシ/パーサー制約の下で、プロファイルを行わない同等条件の実行を比較すること。ストリーム単体の速度低下は、それらの制約が維持されgoodputが向上する場合にのみ許容される。
