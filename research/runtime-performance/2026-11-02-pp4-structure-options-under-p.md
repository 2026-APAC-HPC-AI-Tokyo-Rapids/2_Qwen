## burst の切片（回帰で 0.775〜0.780 s）

先頭 microbatch（41287043170）では、PP0 の result 処理が +286.7 ms、PP3 の result 処理と最後の KV 送信開始が +424.7〜433.7 ms、最初の Decode 出力が +497.7 ms 以前、client の最初の token が +751.1 ms。router は Prefill の応答と Decode の応答を `try_join!` で待ち、Prefill の完了は KV release に結びついているので、Decode の出力から client までの約 253 ms 以上は Prefill 完了通知を待つ経路。結果処理と transfer poll の前倒しは round 10 で採用済み。token の解放だけを早めても平均 ITL が増え、固定 trace の再計算で 100 ms 前倒しは −4.8〜+3.2、300 ms は −78〜−71。token の保持や時間・相に応じた制御は規約上の対象外。

## 選択肢

| 案 | 見込み | 判断 |
|---|---|---|
| burst 中だけ 3 要求の microbatch | 充填遅延で合格が 12〜16 件減り −19〜−26。損益分岐は 1 token あたり約 10.9% の効率改善（既存の見積もりは 1〜3%） | 時間で切り替える制御は対象外。負荷適応でも利益の根拠なし |
| 空いている Decode GPU で Prefill | Basic の構成外 | 除外 |
| 層 24/24/23/23 | 旧 profile の外挿で約 +12（現在の段別の測定なし） | 根拠不足 |
| 層 25/24/23/22 など | 旧 profile の外挿で約 −246 | 採らない |
| PP2×6 worker、PP3×4 worker | 最長段の担当層が増えて相殺し、容量は 52.40 req/s のまま。PP2 は 48 層で約 114 GiB、PP3 は node をまたぐ pipeline が必要。現行 source の高速経路は `pp_size == 4` 専用 | 大改修に対する利益が立たない |
| Decode 上限 48 → 52 | 模型の差 0、最適化 guard を外れて悪化の可能性 | 採らない |
| P13/D3、P14/D2、P8/D8 | D3 は 128 expert が 3 で割れず現行 source で不成立、D2 は約 90 要求/rank が要りメモリ不足、P8/D8 は上限 6,986 | 採らない |
| GPU の入れ替え・router の重み | 容量 ±0.15% 程度、routing だけの容量増は 0 | 採らない |
| CPU・受付の遅延削減 | 50 ms を全て削っても burst で約 +4 | 削れる証拠なし |

## 結論

既存の実測と source で裏付けられる範囲では、10,020 を超える期待利益が、改修費用・未確定要素・run 間の変動を上回る構成・運用の変更はない。再開の条件は、(1) 現在の P で 1 層移動で縮められる段間の不均衡を同一 run の段別 critical time で示す、(2) KV 転送・Decode 開始・release を分けた測定で、計算を遅らせずに両端を前倒しできる固定待ちを示す、(3) PP2 のメモリ・EAGLE・KV 所有まで模型を閉じて容量か実レイテンシの利益を示す、のいずれか。
