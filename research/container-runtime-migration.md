# OCI / Enroot移行記録

## 現行経路

ビルドは、AWSシンガポールリージョンでランごとに一時起動する`m7i.2xlarge`インスタンスにおいて実行する。当該VM上ではroot権限を利用できるため、rootless互換処理を排し、root権限のBuildah、OverlayFS、および`chroot` isolationを用いてDockerfileを処理する。Buildah storageからOCI image layoutへpushし、Skopeoにより別layoutへcopyすることでトランスポート境界を、Umociによりmanifestおよびレイヤー履歴を検証する。検証済みのBuildah作業コンテナ（working container）をroot権限でマウントし、同一のroot filesystemを`-all-root -no-xattrs`オプション付きの`mksquashfs`でSquashFS化する。元環境における厳密なUID/GID、拡張属性（xattr）、およびACLの保持は要件に含めない。

Dockerfileは、システムツールチェーン、NCCL tests、Pythonプロジェクトメタデータ由来の依存パッケージ、GPU通信ライブラリ、およびSGLangソースコードの順序でレイヤーを分割する。SGLangの`pyproject.toml`およびメタデータファイルのみをソースコード本体に先行してコピーし、`uv.lock`をビルド入力に含めずに`uv sync --no-install-project`を実行する。依存関係の解決はコールドビルド時に行い、SGLangソースコードや計測用パッチのみを変更した場合は、解決済みの高コストな依存レイヤーをキャッシュから再利用する。イメージ内に埋め込むマニフェストは最終段階でコピーし、来歴情報の更新のみによってビルドキャッシュが無効化される事態を防ぐ。

VMのルートボリュームには300 GiBのgp3（6,000 IOPS、500 MiB/s）を採用し、Buildahのgraphroot、runroot、ビルドコンテキスト、OCI layout、およびSquashFS作業出力を同一のローカルext4ファイルシステム上に配置する。インスタンスおよびルートボリュームはビルド終了時に確実にterminate（終了）し、異常終了時にも6時間の自動シャットダウンを上限として設定している。これにより、VMおよびEBSの常時課金や、クラスタ共有ファイルシステム上での305〜345 GiBに及ぶVFSキャッシュ保持を廃止し、変更のない中間レイヤーのみを保持数制限付きのプライベートECRへ保存する。

Enroot 4.2.0はDocker archiveやOCI archiveを実行形式として直接マウント・実行できない。そのため、Buildah作業コンテナのroot filesystemを`mksquashfs`によってEnroot用イメージ（SquashFS）へと変換する。OCIイメージの整合性はSkopeoおよび`umoci stat --json`で検証し、Buildahの`chroot`ビルドおよびコンテナ内自己検査を通過した同一のツリーを再利用することで、root filesystemの二重展開オーバーヘッドを排除する。クラスタ側では`.sqsh`ファイルを展開せず、そのファイルパスを`enroot start`へ直接引き渡して実行する。

AWS VM上では32 GiBのRAM全域を一時ビルド作業に割り当てられるため、`mksquashfs`は8ワーカー、8 GiBキャッシュ、gzipレベル2の設定で実行する。オールRAM化は、約26.6 GBのrootfsに加えてBuildahレイヤーデータ、OCI layout、および圧縮処理の入出力を同時に保持すると32 GiBの上限を超過するため採用していない。高速なgp3ボリューム上でOverlayFSのCopy-on-Writeを活用する方が、容量とI/O速度の境界を明確に管理できる。

ビルド成果物は、玄界、ASPIRE 2A+、およびFirmusの各ローカルアーカイブへrun IDを冠した名前で保存する。付随するsidecarファイルは、SquashFSのファイルサイズ、SHA-256、ならびにQwenおよびSGLangのソースコミットを保持する。`[require-build]`が付与されていない実行では、玄界アーカイブを正本としてGitの第一親（first-parent）履歴を遡り、有効な最新ランの成果物を再利用する。プライベートS3の`containers/<Qwen-commit>/<workflow-run-id>-<attempt>/`は、新規ビルド成果物を全3クラスタへ配布する際（保持期間1日）にのみ利用し、完了マーカーは作成しない。再利用時はS3を介さず、各アーカイブ内においてソースランの`.sqsh`およびsidecarを今回のrun IDへハードリンクする。ログインノードへのAWS CLI配置やバケットのパブリック公開は行わず、AWSクレデンシャルをスケジューラジョブ（計算ノード）へ渡すこともない。

## 制御処理の責務

AWSワークフローは、ビルド要否の判定、新規ビルド時のみのS3公開、ならびに3クラスタのアーカイブへのダウンロードまたはハードリンク処理を担当する。各クラスタのワークフローは、ローカルアーカイブからrunディレクトリへの配備およびスケジューラごとの差分吸収のみを担当する。モデル未配置の段階では、3クラスタともにGPUノード上で`sglang.check_env`のみを実行し、従来のダミーモデル、データセット、BigQuery送信、プロファイリング処理は起動しない。

玄界のユーザーローカルなEnroot環境は、アカウントルート直下ではなく、runnerの実ホームディレクトリである`/home/pj26000080/ku60000563/.local`配下に配備されている。ワークフローは、この実在する`etc/enroot`および`lib/enroot`をrunディレクトリへとコピーして使用する。

- `scripts/build-sglang-container.sh`は、root権限でのBuildah、Skopeo、Umoci実行およびSquashFS変換を担当し、`aws/run-build-instance.sh`はS3入出力およびEC2側のログ回収を担当する。
- `scripts/select-qwen-container.sh`は、Gitの第一親履歴を辿る各クラスタのローカル再利用候補の選定、ならびにsidecarと実ファイルの整合性検証のみを担当する。
- `scripts/materialize-qwen-container.sh`は、新規ビルド時におけるBoto3マルチパートダウンロード、および再利用時におけるアーカイブ内ハードリンクの作成を担当する。
- `scripts/provision-qwen-check-env.sh`は、ローカルアーカイブのSHA-256検証、runディレクトリへの配備、およびrun固有Enrootライブラリのマウントポーリング上限値の変更を行う。
- `scripts/run-qwen-check-env.sh`は、計算ノード上にノードローカルなEnroot作業パスを構築し、共有ファイルシステム上にダウンロードされたSquashFSを展開することなく直接起動する。

runディレクトリに配置するスクリプト群は、プロビジョニング実行時のコミットからスナップショットとして固定される。これにより、GitHub Actionsワークフローがキュー待機している間にリポジトリ側が更新されても投入済みジョブの実装内容が変動せず、各ランのコード来歴をコミットOIDに厳密に固定できる。

## クラスタ差

玄界では、ダウンロード先および実行領域を`/fast/pj26000080/sglang-runs`に配置し、`b-batch`の1 GPUノードで動作確認を行う。ASPIRE 2A+では、`/scratch/users/industry/ai-hpc/apacsc14/sglang-runs`を実行領域とし、プロジェクト`59010014`から各ノード112 CPU、8 GPU、1500 GBの構成を`place=scatter:excl`で排他的に要求する。1 GPU、8 CPU、32 GBの非排他割り当てを試行したPBSジョブ`204056.pbs111`および`204057.pbs111`では、部分使用中のノード`a2ap-dgx035`に割り当てられた後、スクリプト本体を一切実行することなく`resources_used.walltime=0`、`Exit_status=-2`、`Stageout_status=1`で終了したため採用しない。小規模な排他要求もサイト側で14 CPU、235 GBのsmall poolへ正規化され空きノード待ちとなった。したがって、過去に成功実績があり実ベンチマークの割り当てとも合致するDGXノード全体の排他要求を採用する。Firmusでは、`/scratch/home/apacsc14/qwen/runs`を実行領域とし、`hpcai`パーティションにおいて1 GPU、8 CPU、32 GB、17分制限で要求する。これはモデル重みを取得しない環境確認用のリソース要求であり、実ベンチマーク実行時は各サイトのノード全体を割り当てるランタイムアダプターへと接続し直してE2E検証を行う。

ASPIRE 2A+において`qsub`の引数としてスクリプトファイルパスを渡すと、全DGXノードを割り当てたジョブ`204058.pbs111`であってもユーザーランドスクリプトの開始前に`Exit_status=-2`で異常終了した。問題の切り分けとして、標準入力（stdin）経由で最小スクリプトを投入したジョブ`204059.pbs111`および`204060.pbs111`では、同一のGPUノード上でシェル、ユーザーID、`~/.local/.setenv`、およびEnrootパスの読み込みまで正常に完了（exit 0）した。一方、同一の検査スクリプトをファイルパス引数で投入したジョブ`204061.pbs111`は、PBS MoMの一時スクリプト`/var/spool/pbs/mom_priv/jobs/204061.pbs111.SC`が実行時に存在せずexit 127となった。このサイト側スクリプトステージングの障害を回避するため、Git管理されたスクリプトの内容を`qsub`の標準入力へリダイレクトして投入する設計とした。

標準入力化を施した後のジョブ`204062.pbs111`も起動前に`-2`となったため、`qsub -v`で渡す環境変数を1つずつ分離して調査した。`RUNTIME_DIR`のみを引き渡して配下の実行ファイルを起動したジョブ`204066.pbs111`はexit 0で完了した一方、同一の最小スクリプトに`CONTAINER_IMAGE`を追加したジョブ`204069.pbs111`は再びスクリプト開始前に`-2`となった。これにより、ASPIREのサイト側フックが`CONTAINER_IMAGE`を予約変数として解釈していることが直接の原因と特定された。別名の中継用環境変数は新設せず、計算ノード側のスクリプトが`RUNTIME_DIR/sglang.sqsh`を直接導出することとし、スケジューラへは`RUNTIME_DIR`のみを引き渡す構成とした。

## 従来のクラスタ内ビルドとGPU dummy実行の記録

以下は、AWS集中ビルドへと移行する前に発生した障害と設計判断の履歴である。

ASPIRE 2A+では、ビルド領域をログインノードの`/dev/shm`に、成果物・実行領域・モデルメタデータを`/scratch/users/industry/ai-hpc/apacsc14`に配置していた。PBSプロジェクト`59010014`を指定し、デフォルトルーティング経由で`aiq2`へ1ノードあたり112 CPU、8 GPU、1500 GBメモリを排他的に要求する運用であった。キュー名`aiq2`を直接指定するとキューACLで拒否され、プロジェクトを指定しなければ計算バジェットを確定できない仕様であった。また、システム標準のEnroot 3.4.1の既定パスは一般ユーザー権限での書き込みが不可能なため、ユーザー領域へEnroot 4.2.0を導入し、キャッシュ、データ、ランタイムパスを書き込み可能な領域へ明示的に設定していた。

Firmusでは、BuildahのVFSキャッシュ、公開成果物、データセット、モデルメタデータ、およびrunディレクトリをBeeGFS上の`/scratch/home/apacsc14/qwen`へ用途別に配置していた。ログインコンテナの`/dev/shm`は63 MiB、`/var/tmp`の空き容量は約184 GiBにとどまり、他クラスタで305〜345 GiBを消費するVFSキャッシュはローカルオーバーレイに収まらなかった。固定digestのBusyBoxによりBeeGFS graphroot上でのBuildah pull、作業コンテナ作成、`chroot`実行、および削除を実証したため、永続graphrootのみを`qwen/buildah`へ置き、runroot、ビルドコンテキスト、OCI layout、SquashFS作業出力は`/var/tmp`へ分離した。完成したSquashFSとsidecarのみを共有成果物として公開する構成とした。計算ノードでは`/tmp`が約894 GiBのノードローカルXFS、`/dev/shm`が約1 TiBであるため、Enroot展開rootfsとJITキャッシュを`/tmp`に、通信ソケットと短命メトリクスを`/dev/shm`に配置した。`hpcai`パーティションの2ノード（各8基のH200）を利用し、サイト上限である17分の制限時間をSlurmアダプターに明示した。

ASPIRE 2A+のhome Lustre環境では、既存の`.local/.setenv`や`.gitconfig`に対して`Cannot send after transport endpoint shutdown`、`Input/output error`、`Network is down`が断続的に発生した。同時刻においてもhome内の新規ファイル作成やscratch、`/dev/shm`への書き込みは成功しており、home使用率は9%、scratch使用率は16%であった。新しいinodeへの置き換えによって読み取りが復旧したため、容量不足や権限不足、ファイルシステム全体の障害ではなく、home Lustreクライアントまたは特定inode/dentryに限定された障害と判断された。再発時はログインノードおよびLustreサーバーのログを管理者に確認依頼する方針とした。

2026-08-23のActions run `32614319756`では、home Lustre障害の再発によりログイン側のrunnerが`.profile`を読み込めず、再利用経路のコンテナ選択前に無条件実行されていた`buildah --version`がexit 127で異常終了した。第一親履歴の成果物再利用において必要なのはGit、sidecarのサイズ・SHA-256検証のみである。Buildah、Skopeo、Umociは新規ビルドスクリプトが、EnrootとNVIDIAフックは計算ノードの実行スクリプトがそれぞれ実際に必要とする時点で検証すれば十分である。高コストな成果物の再利用が無関係なツールチェーンやhomeディレクトリの障害で阻止される事態を防ぐため、両クラスタのselectジョブからコンテナツールの事前プローブ処理を完全に削除した。

全3クラスタにおいて、Enroot実行時にホストの`/dev`全体を再帰的にバインドマウントすることはせず、`ENROOT_RESTRICT_DEV=yes`を指定して最小限のデバイスファイルシステムを構築する。NVIDIAおよびMellanoxのフックは維持し、GPU計算時に必要なデバイスファイルおよびドライバのみをコンテナ内へ注入する。玄界ではPJMのcgroupパスとEnroot 4.2.0の`10-cgroups.sh`が整合しなかったため、このユーザーローカルなフックのみを無効化し、リソース制御をPJM側に委ねた。一方、FirmusのSlurm cgroup環境では標準フックを含めたEnrootの起動が成功しているため、無効化は行わない。

読み取り専用（read-only）のSquashFSから起動するため、計算ノードごとに一時的なruntime homeディレクトリを作成し、コンテナ内の`HOME=/runtime-home`および`XDG_CACHE_HOME=/runtime-home/.cache`へバインドマウントする。JITライブラリが標準キャッシュパスへ書き込みを行う場合もこの単一の書き込み境界に集約し、ライブラリごとにホストのhome配下に対する個別マウントを増やさない設計とした。実行可能な共有ライブラリ（.so）を生成するruntime home、ならびにFlashInfer、DeepGEMM、TorchInductor、Tritonの各ワークスペースは、スケジューラが`TMPDIR`、`TEMPDIR`、`TEMP`の順で指定するノードローカルディスク（未指定時は`/tmp`）上に配置する。さらに、SquashFS直接起動時のマウントヘルパーがSGLang終了時の子プロセス一括killに巻き込まれてstale file handle (Errno 116 / SIGBUS) を引き起こす事態を防ぐため、ノードローカル一時領域配下に`ENROOT_DATA_PATH`/`ENROOT_RUNTIME_PATH`/`ENROOT_CACHE_PATH`/`ENROOT_TEMP_PATH`を設定し、`enroot create`によって展開済みの名前付きコンテナを作成してから`enroot start`を実行する運用とした。ソケットおよび短命なテレメトリのみを`/dev/shm`に残し、用途の異なる一時領域を明確に分離した上で、ジョブ終了時に双方を確実に削除する。

玄界のPJMジョブ`6552532`において、2ノード8 GPU構成でのダミー初期化完了後、`tvm-ffi`がホスト環境由来の読み取り専用`$HOME/.cache`へJIT出力を書き込もうとして失敗した。runtime homeを一旦`/dev/shm`へと移したジョブ`6554500`では書き込み自体は成功したものの、全ランクにおいて生成済み`.so`のロード時に`failed to map segment from shared object`が発生した。過去のSingularity環境での検証と同様、玄界の計算ノード上の`/dev/shm`は実効的に`noexec`設定となっていることが確認されたため、JIT出力先をノードローカルディスクへと戻した。

ASPIRE 2A+のPBSジョブ`203640.pbs111`では、`resources_used.walltime=0`、`Exit_status=-2`、`Stageout_status=1`となり、スクリプト本体の実行前に終了した。このときの`PBS_O_WORKDIR`はephemeral runnerの一時的なcheckoutディレクトリを指していた。ASPIREが採用するPBS 2025.2.2は`qsub -d`オプションを実装していないため、`qsub`実行前にラン固有のscratchディレクトリへと`cd`し、投入時の作業ディレクトリをランのライフサイクルへと固定する処置を施した。玄界でも同一の理由により、`pjsub`実行前にruntimeディレクトリへと移動する。また、プロビジョニング用の`uvx`が利用するマネージドPythonはrunnerの一時領域を利用する一方、後続ジョブでも継続利用する計測CLI用のマネージドPythonはruntimeディレクトリ内に配置し、仮想環境のインタープリタの寿命をランのライフサイクルと一致させた。PBSログが生成されない起動前失敗時であっても、ジョブアカウンティング情報を先行して保存・表示し、成果物として確実に回収する。

玄界の直近の成功ランにおいて、ホスト側ドライバ595.71.05が確認された。一方、固定CUDA 13.0.1ベースイメージ内の`NVIDIA_REQUIRE_CUDA`環境変数は既知の575系ドライバまでしか列挙していなかった。最新ドライバはCUDA 13の要求を満たしているため、GPU実行時は`NVIDIA_DISABLE_REQUIRE=1`をEnrootに明示して古いイメージ内制約のみを無効化する。デバイス、ドライバライブラリ、およびGPUトポロジの整合性は、引き続きNVIDIAフックおよびコンテナ内の`nvidia-smi`によって検証する。また、コンテナ内GPUトポロジのソーススキーマも`singularity_argv`からランタイム非依存の`container_argv`へと移行した。GPUトポロジのプローブは、不変なイメージアーカイブではなく計算ノード上で展開済みのコンテナターゲット（名前付きrootfs）を起動して検査し、SquashFSの不変性照合は`container-sidecar`および来歴管理層へと一元化した。

## 小規模イメージによる実機確認

固定digestのBusyBoxイメージ（`sha256:3c6ae8008e2c2eedd141725c30b20d9c36b026eb796688f88205845ef17aa213`）を用い、DockerfileからのBuildah `chroot`ビルド、作業コンテナに対する`buildah run`、OCI layoutへのpush、Skopeo copy、Umociによるrootless unpack、およびSquashFS作成の各処理が玄界およびASPIRE 2A+のログインノード上で正常に動作することを確認した。さらにASPIRE 2A+において、Buildah VFS作業コンテナのマウント、直接SquashFS作成、OCI push、および`umoci stat --json`を一時BusyBoxイメージで確認した。玄界でもマウントしたVFSツリーからの直接SquashFS作成まで確認済みである。厳密なxattrや元の所有権保持を要求しないため、Lustreファイルシステムが非対応のxattrに対して出力する警告は許容する。

ASPIRE 2A+では、PBSジョブ`203570.pbs111`を1 GPU計算ノード`a2ap-dgx037`へ投入し、小規模`.sqsh`のパスをそのまま`enroot start`へ引き渡して`ENROOT_SMOKE_OK`の出力とexit status 0を確認した。玄界でもPJMジョブ`6548346`を計算ノード`b0004`へ投入し、同様に小規模`.sqsh`の直接起動による`ENROOT_SMOKE_OK`とPJM exit code 0を確認した。FirmusのSlurmジョブ`12613`は1 GPU計算ノード`g4`においてOpen MPI、ノードローカルXFS上のEnroot `create/start`、およびNVIDIAフックを通じてH200とドライバ610.57.04を認識したが、これは展開済みの名前付きrootfsの起動であり、`.sqsh`直接起動の実証ではなかった。2026-08-24のSlurmジョブ`12739`で小規模`.sqsh`の直接起動を試行したところ、同一ノード`g4`上に`/dev/fuse`および`fusermount3`は存在するものの`squashfuse`実行ファイルが存在せず、Enroot 4.2.0はマウント処理前に`Command not found: squashfuse`で終了した。その後、SquashFUSE 0.6.2およびlibfuse 3.18.2を`~/.local`へ導入し、ユーザーローカルな`fusermount3`から計算ノードのシステムヘルパーを指すシンボリックリンクを配置した。Slurmジョブ`12745`は`shared`パーティションの計算ノード`g1`において、root所有かつsetuidされたシステム標準の`/usr/bin/fusermount3`（バージョン3.10.2）、誰でも読み書き可能な`/dev/fuse`、ならびにユーザーローカルなSquashFUSEおよびlibfuseの存在を確認した。共有Enroot環境を変更することなく、ジョブ内の一時コピーにおいて既知の競合対策としてマウントポーリング上限を100回から5000回へ引き上げ、小規模`.sqsh`を直接`enroot start`した結果、`FIRMUS_DIRECT_SQSH_OK`、直接起動時間570,413,934 ns、Slurm exit code 0を達成した。これにより、FirmusにおいてもSquashFS直接起動の基本経路が確立された。検証用イメージ、スクリプト、およびログは確認後に削除し、スケジューラ上に不要なジョブを残していない。

Firmusにおいて直接起動方式を本番運用に採用するにあたり、以下の事項を確認する。

- 本番ランタイムに対してもEnrootのマウントポーリング上限引き上げを適用する。ジョブ`12745`における変更はノードローカルな一時コピーに対する処置であり、共有Enroot環境および現行ワークフローには未反映である。
- 実際の約12.7 GBイメージをBeeGFS上から直接起動し、コールド状態およびウォーム状態におけるそれぞれの起動所要時間、ならびに実行中に必要なブロックのみを読み取るI/O特性を計測する。
- GPU割り当て環境下で、NVIDIAフック、H200 GPU、およびドライバライブラリがコンテナ内から正常に認識されることを確認する。ジョブ`12745`はCPU 1コアおよび1 GiBメモリのみを要求したファイルシステム検証にとどまる。
- 実際のSGLangを起動から終了まで完走させ、マウントヘルパーがプロセスティアダウンに巻き込まれず、stale file handle、SIGBUS、およびunmountの残留が発生しないことを確認する。
- 2ノード実行において、各ノードが同一の`.sqsh`を並行して直接マウント可能であること、ならびにruntime homeおよびJITキャッシュが従来どおりノードローカルなXFS上に配置され、読み取り専用イメージへの書き込みが発生しないことを確認する。

2026-08-23に玄界のCPU計算ノード`a0041`において、実成果物である12,718,784,512バイトのSquashFSイメージ（展開後26,567,442,083バイト、185,800エントリ）を用いて各種起動方式を比較検証した。共有ファイルシステム上のイメージをEnrootから直接起動した場合は0.538秒、`/dev/shm`へ6.861秒かけてコピーしたイメージを直接起動した場合は0.151秒であり、いずれも正常に`/bin/sh`を実行してexit code 0で完了した。カーネルレベルでのSquashFSマウントは、rootlessユーザー名前空間内ではループデバイスの設定に失敗したため利用できなかった。`unsquashfs`を用いて`/dev/shm`へ全展開する処理は11.000秒で完了したが、玄界の`/dev/shm`は`noexec`マウントされているため、展開されたrootfsからの`/bin/sh`実行は`Permission denied`となった。メモリ上のイメージからノードローカルな`/tmp`（XFS）への展開処理は、5分を経過した時点でも進捗が84%にとどまり、実用的な候補とはなり得ないためジョブ`6570638`を打ち切った。このXFS全展開方式は以降の検討対象から除外する。

一方、以前のCPUノード`a0011`において小規模イメージを用いた際は、Enroot直接起動が`fusermount: mount failed: Operation not permitted`で失敗しており、直接FUSE起動の成否にはノード環境またはジョブ投入時の状態による差が存在していた。また、今回の直接起動確認はNVIDIAフックを適用しない短時間のファイルシステム検証であり、既知のマウントヘルパー寿命問題やstale file handle問題が解決したことを証明するものではない。実運用をノードローカル展開から直接起動へ切り替える前に、実際のGPUジョブにおいてNVIDIAフック、SGLangの全実行時間、および正常終了処理までをE2Eで検証する必要がある。

上記の`a0011`での失敗時は標準のEnrootシステム設定を、`a0041`および`a0025`での成功時は空の`ENROOT_SYSCONF_PATH`を使用しており、当初の比較は厳密な同一条件ではなかった。そこで2026-08-24に、当時と同一の1,945,600バイトの小規模イメージ、標準システム設定、`ENROOT_MOUNT_HOME=no`、ノードローカルな`/tmp`上の4系統のEnrootパス、ならびに同一のPJMリソースグループおよび同一の`enroot start`引数を用いる1ノードジョブを4本並行して投入した。その結果、ジョブ`6570976`（ノード`a0128`）、`6570977`（ノード`a0134`）、`6570978`（ノード`a0142`）は成功した一方、ジョブ`6570979`（ノード`a0143`）のみが`Failed to mount`で失敗した。したがって、起動オプションの違いだけでなく、ノード固有の設定またはその時点のノード状態に起因する挙動の差異が実在することが確認された。成功したノード群では、カーネルバージョン4.18.0-477.27.1、Enroot 4.2.0、SquashFUSE 0.6.2、`/dev/fuse`のメジャー／マイナー番号およびパーミッション、ユーザー名前空間の作成状態、PJMデバイスcgroup（`c 10:229 rwm`）、ケーパビリティ、NoNewPrivs、seccompの各項目が完全に一致していた。失敗ノードにおける同一の詳細項目は取得できなかったため、差異の原因がデバイスcgroup、ホスト側のFUSE状態、あるいはその他の潜在的設定のいずれにあるかは未確定である。なお、Enroot外で単体として`squashfuse`を実行すると成功ノードであってもEPERMとなる。Enrootはユーザー名前空間およびマウント名前空間を作成した後にSquashFUSEを起動するため、この単体実行の結果をEnroot可否の判断基準としてはならない。

追加の診断により、この差異は固定的なノード設定の違いではなく、Enroot 4.2.0におけるマウント成立待機の上限回数と起動時間のばらつきに起因する競合状態（race condition）であると特定された。Enrootの`runtime::_mount_rootfs_shim`はSquashFUSEの起動後、`mountpoint`を最大100回ポーリングし、成立が確認できなければ生存中のヘルパーを含むプロセスグループ全体を強制終了する。12ノードでの同時試験を実施したところ、標準設定での初回実行時のみ7ノードで失敗したが、同一ジョブ内での直後の再実行では全ノードが成功した。失敗時と成功時において、名前空間内部のUID/GIDマップ、ケーパビリティ、seccomp、`/dev/fuse`、setuid fusermount、マウントフラグ、およびデバイスcgroup（`c 10:229 rwm`）に一切の差異は認められなかった。標準の100回上限を維持したまま、イメージ、SquashFUSE、fusermount、および共有ライブラリをページキャッシュからパージした計測用ジョブ`6571098`では、ノード`a0061`においてヘルパーが正常生存したまま101回（所要時間340,201,706 ns）に達して`outcome=timeout`で終了した。直前のジョブ`6571083`でもノード`a0059`が成立までに95回（326,555,659 ns）を要しており、制限回数の境界線上にあった。

暫定的な回避策として、Enrootの`runtime.sh`内にある`runtime::_mount_rootfs_shim`のポーリング上限を100回から5000回へと引き上げることで、この競合を確実に回避できる。上限のみを5000回へと変更した一時的なEnrootライブラリコピーを利用したジョブ`6571104`から`6571111`では、同様のコールド条件下において8ノードすべてが正常に成功した。なお、共有Enroot環境の本体には変更を加えていない。恒久的な対策としては、反復回数への依存を排し、十分な実時間（wall-clock）タイムアウトまでヘルパーの生存確認とマウント成立を待機する実装へと改修することをインフラ運用側へ依頼する方針とする。直接SquashFS起動を実運用へ適用する際は、まずGPUジョブ向けのユーザーローカルEnrootに対してポーリング上限の引き上げを適用し、E2Eでの健全性を確認する。

同日の追加PJMジョブ`6570665`および`6570674`において、元イメージと同一の内容を別inodeへ複製し、CPUノード`a0025`上でLinuxの`mincore(2)`を用いて計算ノードのページ常駐率が0%であることを確認した上で直接起動した。この「計算ノードのページキャッシュが完全にコールドな状態」における初回起動所要時間は2.447秒および1.924秒であり、直後の2回目起動では0.133秒および0.132秒へと短縮された。初回起動後にページ常駐したのは全12,718,784,512バイト中わずか444ページ（1,818,624バイト、全体の0.0143%）のみであり、3回目の起動時間も0.134秒および0.136秒で安定していた。イメージ全体をシーケンシャルリードして常駐率を100%にした場合、リード自体に2.794秒および2.762秒を要したが、その後の起動所要時間は0.135秒および0.136秒であり、初回起動によって必要なブロックのみがキャッシュされた状態と比べて速度向上は認められなかった。したがって、起動時間短縮を目的として12.7 GBのイメージ全体を事前に全件読み出す必要はなく、同一ノード上で一度直接起動するだけで十分なキャッシュ効果が得られる。なお、新しいinodeは実験直前に共有Lustre上で作成したため、Lustreクライアント上の該当inodeがコールドであることは実測できるものの、Lustreサーバーおよびストレージデバイス側のキャッシュがコールドであることまでは一般ユーザー権限では保証できない点に留意を要する。

## ダミー実行と計測境界

モデル重み（weights）自体は取得しない。ログインノードのrunnerがHugging Faceから特定リビジョンのモデルJSON、トークナイザー、およびテキストメタデータのみを取得し、ShareGPTについては固定リビジョン`192ab2185289094fc556ec8ce5ce1e8e587154ca`の単一JSONファイルをクラスタごとの共有データセットキャッシュへと取得する。計算ジョブは`--load-format dummy`および固定シードの`random`データセットを指定して分散SGLangを起動する。Enrootの`-m`オプションはコロン区切りのfstab形式であるため、`none:x-create=file,bind,ro,nosuid,nodev`を明示して単一JSONのターゲットファイルを作成し、読み取り専用でマウントしてウォームアップおよび本計測の双方で共用する。データセットのリポジトリ、リビジョン、ファイル名、ホストパス、およびファイルサイズはマニフェストへと記録・検証する。ダミー実行は、コンテナ、GPUインジェクション、MPI/NCCL通信、SGLangの分散起動、メトリクス計測、および成果物回収の一連の流れを確認するための診断処理であり、公式モデルの推論性能を評価するものではない。

玄界のPJMジョブ`6555945`において、ノードローカルディスク上でのJITコンパイルおよび2ノード8 GPU構成でのCUDA graphキャプチャが完了し、従来の`failed to map segment`エラーは解消された。しかしその後、SGLang（コミット`7ec0eb3d7a01f872d0bd2f5095f792c0c1792320`）の`random`データセット処理がShareGPTを暗黙的に外部取得しようとし、計算ノードの`HF_HUB_OFFLINE=1`境界によって通信が遮断され異常終了した。

最初の再検証となったActions run `32536408333`では、PJM投入前のプロビジョニング段階において、計測ライブラリの閉スキーマ検証が旧来の`random`値を要求したため`dummy dataset manifest differs`となって失敗した。これを同期させたPJMジョブ`6556998`では、データセットレジストリに存在する`random-ids`を`offline_throughput.py`のCLI選択肢が受理せずexit 2となった。また同CLIは、選択されたデータセットにかかわらずShareGPT由来のランダムウォームアップデータを先行構築する仕様であるため、`generated-shared-prefix`へ変更するだけでは暗黙の外部ダウンロード処理が残存する。そこで、ShareGPTをログインノード側で事前取得して公式の`random`データセット経路へと明示的に与えることで、計算ノードのオフライン境界を維持しつつ、入力1024トークン、出力128トークン、8プロンプトの診断条件を成立させた。これはランタイム入力と来歴管理のみの変更であり、コンテナの再ビルドを必要としない。なお、過去ランのマニフェストおよび成果物は書き換えない。

玄界のActions run `32550368591`（PJMジョブ`6558594`）において、2ノード8 GPU構成でのダミー生成が8件すべて成功し、ベンチマークステージもexit code 0で完了した。しかし、`primary-result/v1`が厳密な十進表現として文字列`"2.342779523"`を出力したのに対し、後段の成功判定処理がjqの数値型のみを抽出する`numbers`フィルタを使用していたためexit code 4となり、`run-success`マーカーが生成されなかった。このため、成功判定処理を計測契約に準拠させ、文字列・数値の双方を受理して正の数値へと正規化する`tonumber`を用いるよう改修した。なお、ノード1において観測された生のwait status 9およびGlooのpeer resetは、ランク0の終了に伴う分散SGLangの正常なティアダウン過程で発生したものであり、ベンチマークステージ自体の判定結果ではなく、今回のActionsジョブ失敗の直接原因ではない。
