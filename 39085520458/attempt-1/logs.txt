2026-10-18T01:10:52.8728573Z   QWEN_COMMIT_MESSAGE: Measure several DeepGEMM candidates and an SGLang JIT-kernel candidate in one Firmus kernel bench job

Motivation: Firmus has two H200 nodes in partition hpcai and other teams keep
about eight two-node jobs queued, so every GPU job waits a long time. Until
now one kernel-bench push measured exactly one DeepGEMM overlay, and SGLang
JIT-kernel candidates had no kernel-only path at all. Several workers
(MegaMoE Prefill, MegaMoE Decode, SGLang JIT kernels) are about to iterate on
candidates; packing several candidates into one Slurm job cuts their job count
from 5-10 to 1-3.

Layout (the flat patches/deep-gemm-bench/*.patch form is migrated, not kept):
- patches/deep-gemm-bench/<name>/*.patch: one directory per DeepGEMM
  candidate, patches applied in name order relative to site-packages on top
  of the image's deep_gemm, exactly as before. Names match
  [a-z0-9][a-z0-9._-]*, "image" is reserved. Flat *.patch files directly in
  patches/deep-gemm-bench are rejected by provisioning with a message, so an
  old-style branch fails before Slurm instead of silently measuring nothing.
- An empty file named "timeline" inside a candidate directory requests the
  instrumented timeline run for that candidate; patches/deep-gemm-bench/timeline
  requests it for the image. Timeline is opt-in because the timeline patch's
  context lines may collide with a candidate. If it does not apply, the
  git apply error goes to logs/timeline-apply-<name>.log, that timeline is
  skipped, and the summary marks the candidate FAILED; the job continues.
- patches/sglang-bench/*.patch: applied with git apply (paths python/sglang/...,
  like patches/sglang) to a copy of the image's /opt/sglang/source/python/sglang
  extracted by unsquashfs during provisioning (94 MB, about 4 s on the login
  node), placed first on PYTHONPATH for a dedicated step. The image's sglang
  is an editable install whose finder is appended to sys.meta_path, so the
  PYTHONPATH tree wins; the step asserts which tree sglang.kernels.jit came from.

Job flow (platforms/firmus/kernel-bench/run.sbatch):
1. image bench first, as the in-job reference (clock drift is visible inside
   one job); a failure here stops the job because nothing can be compared.
2. image timeline when requested.
3. SGLang step when patches exist: check-firmus-decode-kernels.py for the
   image tree and the patched tree, then scripts/bench-firmus-sglang-kernels.py
   for both when that script exists. The candidate builds its JIT kernels in
   TVM_FFI_CACHE_DIR=scratch/tvm-ffi-candidate (sglang.kernels.jit keys its
   build dir on TVM_FFI_CACHE_DIR and a source hash), so it always recompiles;
   the image tree keeps the default cache under HOME shared with the gates.
   Bench script contract: python bench-firmus-sglang-kernels.py --output <jsonl>
   --variant <image|candidate>, single process (cuda:0), one JSON object per
   case with case, median_us, p10_us, p90_us, output_sha256; JIT and
   correctness outside the timed region; non-zero exit on failure.
4. per DeepGEMM candidate: numerical gate, timing bench with --reference
   results/image/bench.jsonl (rows record output_sha256_matches_reference and
   the delta), and the timeline when staged. A failed gate skips the rest of
   that candidate only.
Every step appends variant, step, exit code and seconds to results/steps.tsv
and the job continues. Per-candidate scratch directories keep each variant's
saved timeline reference outputs apart.

Verdict: scripts/summarize-megamoe-kernel-bench.py reads variants.json (written
by provisioning: candidates, patch SHA-256s, timeline state, SGLang patches),
steps.tsv and the results, prints a verdict, a candidate status table (gate,
bench, hashes equal to image, timeline, verdict), one side-by-side median table
with delta vs image, a detail table (median/p10/p90, delta, slowest-GPU SM
clock, clock-normalized delta, power, rank load, determinism, hash match), the
timeline overhead table and phase reports, and the SGLang table. It exits 1 on
any failed step, hash mismatch, missing case, timeline apply failure, or SGLang
hash mismatch, which fails the Actions summary step and makes the run red.
check-job.sh now only requires that the Slurm job completed and the image
bench exists. Archives from the single-candidate layout need the summary
script as of 332e30c.

GPU clock record: bench-firmus-megamoe.py reads each rank's SM clock and power
through NVML (torch.cuda.clock_rate / power_draw, nvidia-ml-py is in the image)
right before the barrier that starts the timed iterations and right after their
synchronize, outside the CUDA event pair, and gathers them per case. NVML is
initialized once before the first case so no case pays the init cost. An
nvidia-smi subprocess was rejected because it would leave the GPUs idle for
hundreds of milliseconds right before the timed loop and let the power budget
recover, changing exactly the Prefill behavior being measured.

Time limit: the request was to raise the 17-minute Slurm limit to about 35
minutes, but scontrol shows hpcai MaxTime=00:17:00 and our QoS normal has
MaxWall 17 minutes, so the limit stays. From run 39066974393 one candidate
costs gate about 70 s + bench about 40 s + timeline about 35 s, and the image
bench about 70 s with a cold DeepGEMM JIT cache. Provisioning therefore rejects
more than 4 DeepGEMM candidates (4 with timelines plus the image and an SGLang
